# Правила работы в репозитории

## Ветки

- `main` — продакшен-ветка.
- `dev` — основная ветка разработки и ветка по умолчанию.
- Всегда начинай новую работу от актуального состояния `dev`.
- Для новой функциональности создавай отдельную ветку от `dev`; после завершения направляй изменения в `dev`.

## Попадание изменений в `main`

- Не делай прямые commit и push в `main`.
- Не переключайся на `main` для разработки и не используй его как рабочую ветку.
- Изменения в `main` переносятся только через pull request из `dev` в `main`.
- До merge pull request `dev` → `main` должен получить минимум один approving review.
- Не выполняй merge в `main` без требуемого апрува, даже если локальный Git или права администратора позволяют это сделать.
- Не отключай и не ослабляй защиту `main`, не обходи её через force push или административные привилегии.
- Перед созданием pull request в `main` проверь, что изменения протестированы и готовы к продакшену.

## Рабочий процесс AI-агента

1. Проверь текущую ветку перед любыми изменениями.
2. Убедись, что рабочая ветка основана на `dev`.
3. Не добавляй в коммиты секреты, API-ключи, локальные окружения и временные файлы.
4. После изменений выполни подходящие проверки и опиши их результат.
5. Не создавай pull request в `main` и не выполняй его merge без явного запроса пользователя; наличие запроса не отменяет требование апрува.

## Проект

ИИ-консультант МТС EnergyTool (кейс Hack&Change 2026). Устройство решения и команды — в `README.md`.

- `energybot/` — общее ядро: база знаний, поиск, диалог, промпт, клиент LLM. Его используют и `solution.py` (автопроверка), и будущий веб-чат — не дублируй логику в точках входа.
- `solution.py` — точка входа платформы: `DATA_DIR/questions.csv` + `knowledge-base.zip` → `submission.csv` (`id,answer`).
- `eval/` — локальный стенд оценки и проверочная выборка, `tests/` — офлайн-тесты.

## Источник истины и данные

- Факты бота о продуктах, ценах, сроках, порогах и нормативах — только из `knowledge-base/`. Не добавляй в промпты, эталоны и тесты знания модели или данные сайта energytool.mts.ru: часть цифр на сайте расходится с базой, верна база.
- Если факта нет в базе, правильное поведение бота — сказать об этом и предложить специалиста.
- Репозиторий приватный: по правилам кейса базу знаний нельзя публиковать. Не делай репозиторий публичным и не выкладывай материалы кейса в открытые места.
- Используй только тестовые или выдуманные персональные данные.

## Решение для автопроверки

- Требования платформы — в `docs/tech-regulations.pdf` (оригинал) и `docs/tech-regulations.md` (текстовая копия); при сомнениях сверяйся с PDF.
- `solution.py` обязан всегда оставлять валидный `submission.csv`: непустой ответ на каждый ID, сбой LLM, эмбеддингов или реранкера не должен ронять прогон; прогон укладывается в 20 минут (`EB_DEADLINE_SEC`).
- Зависимости сабмита — только из `solution-requirements.txt`, и только из разрешённого набора `requirements.txt` организаторов; код должен работать на Python 3.9+.
- Адреса API, ключи и модели берутся из переменных окружения; ничего не захардкоживай. Свои настройки решения называй с префиксом `EB_`: платформенные `TOP_K`, `MAX_TOKENS`, `TEMPERATURE` настроены под бейзлайн.
- ZIP собирай только через `scripts/build_submission.py`: он кладёт в корень архива только `.py` и `requirements.txt` (пакет `energybot/` превращается в `eb_*.py`). Никаких вложенных папок, индексов, данных, базы знаний и `.env`. Импорты внутри `energybot/` пиши в форме `from .module import …` — их умеет переписывать сборка.
- В режиме автопроверки бот не предлагает оставить заявку и не просит контакты: судья сравнивает с эталонами, где этого нет. Сбор заявки — только в веб-чате.

## Проверки перед pull request

- Всегда: `.venv/bin/ruff check .` и `.venv/bin/python -m unittest discover -s tests`; CI (`ci.yml`) должен быть зелёным.
- Сабмит: `.venv/bin/python scripts/check_submission.py` — 0 непройденных проверок.
- Изменил поиск, нарезку базы или промпт — прогони `eval/retrieval_eval.py --split dev` (главная метрика — доля разделов эталона в контексте) и, если есть ключ, `eval/run_eval.py --with-demo --baseline`; приложи метрики «до/после» в описание PR.
- Изменил число вызовов модели, контекст или параллельность — прогони `scripts/simulate_budget.py`: прогон обязан укладываться в 20 минут без пустых ответов.
- Не ослабляй проверку ответа (`energybot/guard.py`) без замера: на эталонах выборки она не должна срабатывать против всей базы.
- Подбирай промпт и поиск по `dev`. `holdout` запускай редко, только для контрольной проверки, и не подгоняй под него решение.

## Проверочная выборка

- Формат и правила кейса — `eval/dataset/SPEC.md`. Правь только `eval/dataset/parts/*.jsonl`, затем запускай `eval/validate_dataset.py eval/dataset/parts/*.jsonl` (0 ошибок) и `eval/build_dataset.py`. `cases.jsonl` руками не редактируй.
- Эталон — в стиле ответов жюри (`demo_output.csv`), каждое утверждение подтверждено разделами из `sources`.
- Не копируй вопросы из `demo_questions.csv` в выборку.
- `must_not` пиши как утвердительное нарушение («гарантируем», `^да\b`): проверка не засчитывает совпадение, если во фразе есть отрицание.

## Не коммить

- `.env` и любые ключи — только `.env.example` без значений.
- `.venv/`, `dist/`, `eval/reports/`, `submission.csv`, `debug.jsonl`.
