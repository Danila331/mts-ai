# 0004. Go-API отдельно от Python-ядра

- Статус: принято, реализовано
- Дата решения: 2026-11-11 (коммит `243fca4`, PR #22); запись — 2026-11-15
- Код: `backend/` (Go-API), `scripts/core_api.py` (внутренняя служба ядра), `energybot/` (ядро)

## Контекст и проблема

Ответ строит ядро `energybot/` — тот же код, что у сабмита `solution.py`. Ядро обязано работать на Python 3.9+ и
только с зависимостями сабмита (`httpx`, `numpy`), а логику нельзя дублировать в точках входа (`AGENTS.md`).

Первый веб-API стенда был на Python (`scripts/web_api.py`) и хранил заявки и оценки в `web/.data/*.jsonl` —
контейнер хостинга теряет их на каждой выкладке (сообщение коммита `243fca4`). Публичному API нужно ещё:
Postgres с миграциями, пределы частоты на несколько реплик, токен прокси, поток ответа, аккуратная остановка,
журнал и метрики, сроки хранения ПДн.

## Факторы решения

- Ядро одно для сабмита и стенда; его зависимости не растут.
- Публичная поверхность и ядро, которое тратит деньги на модель, должны быть разделены границей доверия.
- Заявки и журнал переживают выкладку.
- Контракт с фронтом (`web/src/lib/types.ts`) не меняется.

## Рассмотренные варианты

1. **Оставить всё в Python:** API, база, пределы — в той же службе, что ядро.
2. **Всё на Go:** переписать поиск и промпт.
3. **Сервер Next ходит в ядро напрямую**, база — из Next.
4. **Go-API снаружи, Python-ядро внутри**: ядро только строит ответ.

## Решение

Вариант 4. Go-API (`backend/`: echo, pgx, sqlc, golang-migrate, zerolog) принимает запросы прокси Next, держит
пределы частоты (Redis), пишет заявки, оценки и журнал ответов в Postgres, пересылает поток ядра, чистит ПДн по
сроку и удаляет по запросу. Ядро (`scripts/core_api.py`) — только стандартная библиотека поверх `energybot/`,
наружу не публикуется, отвечает только с `EB_CORE_TOKEN`.

Почему не остальные:

- **Всё в Python** тянуло бы драйвер Postgres, Redis и веб-фреймворк в службу, которая должна совпадать с
  сабмитом по зависимостям (`core/Dockerfile` ставит только `solution-requirements.txt`). Публичная служба и
  дорогое ядро оказались бы одним процессом.
- **Всё на Go** — второе ядро: поиск и промпт разошлись бы с сабмитом, а качество меряется на сабмите
  (`eval/`). Это прямо запрещено `AGENTS.md`.
- **Next напрямую в ядро** — бизнес-логика заявок, база и пределы жили бы в функциях Vercel; ядро пришлось бы
  открыть в интернет.

## Последствия (цена решения)

- Хорошо: ядро не видно снаружи; без токена прокси Go-API в бою не стартует (`config.Verify`). Ключ api у шлюза
  даёт только `energy-chat` (`llm-gateway/keys.py`).
- Хорошо: заявка сохраняется до резюме моделью; без модели — с резюме-списком вопросов
  (`summary_source = digest`).
- Плохо: два языка и два набора проверок (`make -C backend lint test` и `ruff` + `unittest`).
- Плохо: правила чистки диалога продублированы — `backend/internal/dialog/dialog.go` и `clean_turns` в
  `scripts/core_api.py` (40 реплик, 4000 символов). Разойдутся — Go пропустит то, на что ядро ответит отказом
  посреди потока. Синхронность держится комментариями в обоих файлах, общего теста нет.
- Плохо: лишний сетевой переход и ещё один секрет (`EB_CORE_TOKEN`).

## Замеры

Замера нет: задержка, которую добавляет Go-API, не измерялась (нагрузочный тест — T32).
