# 0002. Гибридный поиск BM25 + bge-m3 через RRF, затем реранкер

- Статус: принято, реализовано
- Дата решения: 2026-11-09 (коммит `cad94ee`); запись — 2026-11-15
- Код: `energybot/retrieval.py` (`BM25`, `Retriever.candidates`, `Retriever.search`), `energybot/text.py`,
  `energybot/llm.py` (`embed`, `rerank`), `scripts/index_cache.py`

## Контекст и проблема

RAG (ADR [0001](0001-rag-instead-of-fine-tuning.md)) хорош настолько, насколько поиск приносит в контекст разделы,
на которые опирается эталон. Клиенты пишут разговорно («счётчик», «воровство», «крыша»), а в базе — термины
(«прибор учёта», «потери», «кровля»): словарь таких замен — `SYNONYMS` в `energybot/text.py`. Регламент даёт для поиска bge-m3 и Qwen3 Reranker 8B, реранкер необязателен
(`docs/tech-regulations.md`, раздел 7). Сабмит обязан ответить на каждый вопрос, даже если API эмбеддингов или
реранкера упал (`AGENTS.md`).

## Факторы решения

- Главная метрика — доля разделов эталона в контексте (`eval/retrieval_eval.py`).
- Точные совпадения терминов и чисел (750 кВт, ОРЭМ) важны не меньше смысловой близости.
- Каждая ступень должна уметь отказать без потери ответа.
- Зависимости сабмита — только `httpx` и `numpy` (`solution-requirements.txt`): никаких поисковых движков.

## Рассмотренные варианты

1. **Только BM25** — со своей токенизацией, лёгким русским стеммером и разговорными синонимами.
2. **Только векторы bge-m3.**
3. **Гибрид со взвешенной суммой скоров** BM25 и косинуса.
4. **Гибрид через Reciprocal Rank Fusion (k = 60)**, затем реранкер упорядочивает кандидатов.

## Решение

Вариант 4. Каналы — BM25, при включении символьные n-граммы, bge-m3 — сливаются по рангам RRF с k = 60
(`Retriever.candidates`), реранкер Qwen3 упорядочивает 20 кандидатов (`EB_N_CANDIDATES`), в контекст идут
10 лучших фрагментов (`EB_TOP_K`) и соседние разделы главного документа в пределах 18 тыс. символов
(`EB_CONTEXT_CHARS`). Всегда подмешиваются общие границы консультации (`ALWAYS_DOC`).

Лестница деградации: нет эмбеддингов — BM25; нет реранкера — порядок RRF; ядро стенда достраивает векторы в фоне
раз в `EB_DENSE_RETRY_SEC` (30 с), если на старте модель не ответила (`scripts/core_api.py`, `retry_dense`).

Почему не остальные:

- **Только BM25** — замер ниже: эмбеддинги добавляют долю найденных разделов.
- **Только векторы** — без BM25 нет пути при недоступном API эмбеддингов, а сабмит не имеет права упасть.
  Отдельного замера «только векторы» нет.
- **Взвешенная сумма** требует нормировать несравнимые шкалы BM25 и косинуса и подбирать вес. RRF работает
  по рангам и подбора не требует. Замера взвешенной суммы против RRF нет.

## Последствия (цена решения)

- Плохо: два дополнительных сетевых вызова на вопрос (эмбеддинг запроса, реранк) — время и деньги.
- Плохо: векторы всей базы нужно посчитать до первого ответа. На стенде это минуты на первом старте (`README.md`,
  «Запуск»), дальше — кеш по хешу текстов и отпечатку модели (`scripts/index_cache.py`, переменная
  `EB_INDEX_CACHE_DIR`).
- Плохо: векторы разных моделей несовместимы. Смена модели эмбеддингов — полная переиндексация, запаса другой
  моделью у `energy-embed` быть не может (`llm-gateway/config.yaml`).
- Хорошо: отказ любой ступени не роняет ответ; в отладке стенда видно, какие ступени работали
  (`/api/health`: `dense`, `reranker`).

## Замеры

Из `README.md`, раздел «Текущие метрики поиска»: 291 кейс рабочей части выборки без вопросов вне базы.

| Контекст | все разделы эталона в контексте | доля найденных разделов | размер контекста |
|---|---|---|---|
| было: 6 фрагментов | 0.30 | 0.53 | ~7 тыс. символов |
| 10 фрагментов + разделы главного документа (BM25) | 0.63 | 0.77 | ~17,7 тыс. символов |
| то же + эмбеддинги (гибрид, без реранкера) | 0.71 | 0.84 | ~16,5 тыс. символов |

Оговорки из того же раздела: гибрид мерили на `qwen3.7-text-embedding`, а не на `bge-m3` платформы — это порядок
прироста, а не точная цифра. «Главный документ первым»: 0.52 → 0.58 с эмбеддингами.

**Вклад реранкера — замера нет.** В `README.md` прямо сказано: «Эмбеддинги и реранкер должны поднять порядок;
проверим, когда будет доступ к модели».

Воспроизвести: `.venv/bin/python eval/retrieval_eval.py --split dev --verbose` (без ключей — BM25, с ключами —
гибрид).
