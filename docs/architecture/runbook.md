# Runbook

Что делать, когда что-то пошло не так. Команды — для стенда из `compose.yaml` (из корня репозитория) и, где
отличается, для Railway (`docs/deploy.md`). Состав служб и секреты — [`README.md`](README.md).

Первый экран при любой проблеме (переменные — из `.env`: `set -a; source .env; set +a`):

```bash
docker compose ps                                        # все службы healthy?
docker compose logs --tail=200 api core llm-gateway      # журналы трёх служб ответа
curl -s -H "Authorization: Bearer $EB_API_TOKEN" http://127.0.0.1:8787/api/health   # ядро: llm, dense, reranker, chunks, db
```

Тревоги — http://localhost:9090/alerts (правила `monitoring/rules.yml`; Alertmanager не подключён, уведомлений нет).
По `request_id` из заголовка `X-Request-ID` ответа строка находится в журналах api и ядра и в колонке
`request_id` таблиц `answers` и `leads`.

## С чего начать: дашборды Grafana

Локально http://localhost:3001 (`admin` и `GF_SECURITY_ADMIN_PASSWORD`), на Railway — служба `grafana`
(`docs/deploy.md`, 3b). Какие тревоги сработали — вкладка Alerts в Prometheus (:9090); доставки в Telegram нет.

| Симптом | Дашборд и панели | Дальше |
|---|---|---|
| Клиенты видят заглушки | «Консультант» → «Исходы ответов», «Ответов не от модели, %»; затем «Модель и шлюз» → «Ошибки провайдера по моделям», «Запас: сработал и не помог» | «Модель недоступна» |
| Ответы долгие или потоки копятся | «Консультант» → «Длительность ответа чата, p50 и p95», «Открытые потоки ответа»; «Модель и шлюз» → «Задержка ответа провайдера» | «Модель недоступна» |
| Много отказов «слишком много запросов» | «Консультант» → «Отказы по пределу частоты (429)» (по правилам), «Модель и шлюз» → «Ошибки запросов по службе» (429 ключа службы) | «Всплеск 429» |
| Расход выше ожидаемого | «Модель и шлюз» → «Расход по службе», «Токены на входе/на выходе по службе» (`api_key_alias`: core или api) | ключи и бюджеты: `llm-gateway/README.md` |
| Заявки приходят без резюме | «Заявки» → «Заявки по источнику резюме» (`digest` — без модели) | «Модель недоступна» |
| Нет данных на панелях | Prometheus → Status → Targets: цели `api`, `llm-gateway` в `UP`; в Grafana → Connections → Data sources → Prometheus → Test | `monitoring/` |

## Модель недоступна

**Признаки.** Тревоги `LlmGatewayDown` (шлюз молчит 2 мин), `ChatAnswersDegraded` (больше 20% ответов за 10 мин —
не ответ модели), `LeadSummariesWithoutModel` (больше половины заявок за час — без резюме моделью). Клиент видит
отказ-заглушку «Точного ответа на этот вопрос в моих материалах нет…» (`FALLBACK` в `energybot/pipeline.py`).

**Что уже делает система сама.**

- Ядро повторяет 429/5xx до 3 раз с паузой (`energybot/llm.py`, `_post`), потом отвечает заглушкой.
- Шлюз при 429/5xx/тайм-ауте уходит в `energy-chat-fallback`, если заданы `GW_FALLBACK_*`; после 2 сбоев за минуту
  выводит основного из ротации на 30 с (`llm-gateway/config.yaml`). Без запаса — только повторы клиента.
- Без эмбеддингов поиск работает на BM25 и достраивает векторы в фоне раз в `EB_DENSE_RETRY_SEC` (30 с).
- Заявки принимаются: сохраняются до резюме, без модели — со списком вопросов (`summary_source = digest`).

**Проверить.**

```bash
# шлюз жив и ключи служб синхронизированы — та же проверка, что healthcheck в compose.yaml
docker compose exec llm-gateway python -c "import os, urllib.request; urllib.request.urlopen('http://127.0.0.1:4000/health/liveliness', timeout=2); assert os.path.exists('/tmp/gw-ready'); print('ok')"
docker compose logs --tail=200 llm-gateway | grep -iE "error|429|5[0-9][0-9]|timeout"
```

В Prometheus — исходы ответов: `sum by (outcome) (rate(eb_chat_answers_total[10m]))`.

Если шлюз жив, а провайдер отвечает ошибками — проблема у провайдера (ключ, баланс, лимиты, авария).

**Действия.**

1. Включить запасного провайдера той же модели: в `.env` задать все три `GW_FALLBACK_BASE_URL`,
   `GW_FALLBACK_API_KEY`, `GW_FALLBACK_CHAT_MODEL`, затем `docker compose up -d llm-gateway`. На Railway — те же
   переменные у службы `llm-gateway`. Другую модель в запас — только после прогона `eval/` (`llm-gateway/config.yaml`).
2. Сменить основного провайдера — поменять `GW_*` шлюза (локально — `LLM_BASE_URL`, `LLM_API_KEY`, `LLM_MODEL` в
   `.env`) и перезапустить только шлюз. Ядро и api не трогаются.
3. Если шлюз стартовал без модели, а потом модель настроили — перезапустить ядро: `docker compose restart core`.
   Ядро запоминает, что параметр размышлений «не поддерживается» (`llm-gateway/README.md`).

**После.** `/api/health` → `"llm": true`, `"dense": true`; `smoke.sh` проходит:
`sh backend/scripts/smoke.sh http://127.0.0.1:8787 "$EB_API_TOKEN" http://127.0.0.1:3000`.

**Чего нет.** Показа фрагментов базы вместо заглушки и баннера деградации в виджете — T30.

## Всплеск 429

429 приходит из трёх мест, и лечатся они по-разному.

| Откуда | Как узнать | Что делать |
|---|---|---|
| Пределы Go-API по адресу клиента | тело ответа: «Слишком много вопросов подряд…», «Заявок с этого адреса слишком много…»; метрика `eb_rate_limited_total{rule}` | см. ниже |
| Ключ службы в шлюзе (`rpm_limit`) | в журнале ядра — ошибки вызова модели, клиент получает заглушку; метрики LiteLLM по `api_key_alias` | поднять `GW_KEY_CORE_RPM` / `GW_KEY_API_RPM` (умолчания 240 и 60), `…_PARALLEL` (16 и 4) у шлюза и перезапустить его — `keys.py` обновит ключи при старте |
| Провайдер модели | 429 в журнале шлюза | запасной провайдер (`GW_FALLBACK_*`), иначе — договориться о лимите у провайдера |

**Пределы Go-API.** Отдельной тревоги на 429 нет — смотреть вручную:

```promql
sum by (rule) (rate(eb_rate_limited_total[5m]))
```

1. **Один адрес или все?** В журнале api у каждой строки запроса есть поле `ip`:
   `docker compose logs --since 10m api | grep 429`. Если у всех отказов один и тот же адрес (адрес
   Vercel или прокси) — до API не доходит адрес посетителя: проверить, что прокси Next шлёт `X-Client-IP`, а у api
   задан `EB_API_TOKEN` (без токена API не верит этому заголовку, `clientIP` в
   `backend/internal/transport/http/server.go`). Тогда все посетители делят один предел.
2. **Один адрес — скрипт или бот.** Пределы работают как задуманы. Блокировки по адресу в коде нет — при
   необходимости закрыть адрес на уровне хостинга.
3. **Настоящий наплыв людей.** Поднять пределы в `.env` (`EB_LIMIT_CHAT_PER_MINUTE`/`_BURST`, `EB_LIMIT_LEAD_PER_HOUR`/
   `_BURST`, `EB_LIMIT_FEEDBACK_PER_MINUTE`/`_BURST`, `EB_LIMIT_SETTINGS_PER_MINUTE`/`_BURST`) и пересоздать api:
   `docker compose up -d --force-recreate api`. На Railway — переменные службы `api`. Ноль в бою не пройдёт проверку
   конфигурации на старте.
4. Тревога `RateLimitStoreFailing` — Redis недоступен, пределы считаются в памяти каждой реплики (с несколькими
   репликами фактический предел выше заданного). Поднять Redis: `docker compose up -d redis`.

## Переиндексация и откат

Когда нужна: правка `knowledge-base/`, нарезки (`energybot/kb.py`) или смена модели эмбеддингов.

Как устроен индекс: база вшита в образ ядра (`core/Dockerfile`), векторы ядро считает на старте и кладёт в кеш
`EB_INDEX_CACHE_DIR` (`/data/index`, том `core-index`). Ключ кеша — хеш текстов фрагментов и отпечаток модели по
контрольной фразе; хранятся 3 последние версии (`KEEP` в `scripts/index_cache.py`). Новая база или новая модель —
новый каталог и полный пересчёт (минуты на первом старте, `README.md`); возврат к прежней — попадание в кеш и один
запрос к модели.

**До выкладки** (`AGENTS.md`):

```bash
.venv/bin/python eval/retrieval_eval.py --split dev        # доля разделов эталона в контексте — не хуже, чем было
.venv/bin/python -m unittest discover -s tests
.venv/bin/python scripts/check_submission.py               # 0 непройденных проверок
```

**Выкладка.** Локально — `docker compose up -d --build core`. На Railway — слияние в `main`: Watch Paths службы
`core` включают `/knowledge-base/**` и `/energybot/**`, выкладка ждёт зелёный CI; healthcheck ядра — до 300 с
(`docs/deploy.md`, раздел 2).

**Проверка после.**

```bash
docker compose logs core | grep "индекс готов"     # from_cache, saved, took_ms
curl -s -H "Authorization: Bearer $EB_API_TOKEN" http://127.0.0.1:8787/api/health   # kb_fingerprint, chunks, dense
```

`"dense": false` сразу после выкладки — модель эмбеддингов не ответила на старте; ядро отвечает на BM25 и
достраивает векторы в фоне.

**Откат.** Вернуть прежнее содержимое базы новым коммитом (`git revert <коммит>`) и выложить тем же путём: на
Railway — через PR `dev` → `main` с апрувом (`AGENTS.md`), локально — `docker compose up -d --build core`. Если
версия была среди трёх последних, векторы возьмутся из кеша.

**Принудительный пересчёт** (кеш подозрителен):

```bash
docker compose exec core sh -c 'rm -rf /data/index/*' && docker compose restart core
```

**Откат настроек RAG**, если кто-то с правами администратора сломал бота для всех: настройки живут в памяти ядра
до перезапуска, поэтому хватает одного из двух.

```bash
curl -s -X POST -H "Authorization: Bearer $EB_API_TOKEN" -H "X-Admin-Token: $EB_ADMIN_TOKEN" \
  http://127.0.0.1:8787/api/settings/reset          # вернуть значения из окружения
docker compose restart core                        # или перезапустить ядро
```

## Утечка ключа

Порядок для любого секрета: выпустить новый → поставить его всем, кто его знает (таблица в [`README.md`](README.md))
→ перезапустить их → отозвать старый → проверить `smoke.sh`. Новые значения — `openssl rand -hex 32` для токенов,
`sk-` + `openssl rand -hex 24` для ключей шлюза (`docs/deploy.md`).

| Утёк | Чем опасен | Где поменять | Особенности |
|---|---|---|---|
| Ключ провайдера (`LLM_API_KEY` → `GW_API_KEY`) | расход у провайдера с чужих машин | `.env` / переменные службы `llm-gateway`; перезапустить шлюз | отозвать старый ключ в кабинете провайдера — главное действие; проверить расход там же |
| `GW_FALLBACK_API_KEY` | то же для запасного провайдера | там же | то же |
| `LITELLM_MASTER_KEY` | управление шлюзом и ключами служб | шлюз | после смены выпустить и новые `GW_KEY_*`: владелец мастер-ключа мог создать свои ключи |
| `GW_KEY_CORE`, `GW_KEY_API` | вызовы моделей в пределах ключа (у api — только `energy-chat`) | шлюз и служба-потребитель (`core` → `LLM_API_KEY`, `api` → `LLM_API_KEY`); сначала шлюз, потом потребитель | `keys.py` создаёт новый ключ, но **старый из базы шлюза не удаляет** — удалить вручную через API управления ключами LiteLLM мастер-ключом (в репозитории команды нет, сверить с документацией LiteLLM `1.108.9`) |
| `EB_API_TOKEN` | прямой доступ к Go-API в обход прокси и право задавать `X-Client-IP` | `api` и `web` (Vercel) одновременно | между выкладками двух служб прокси получает 401 — менять в тихое время |
| `EB_ADMIN_TOKEN` | смена настроек RAG для всех | `api` и `web` (Vercel) | cookie администратора — HMAC от токена, смена выводит из всех сессий сама; после смены — откат настроек (`/api/settings/reset`) |
| `EB_CORE_TOKEN` | прямые вызовы ядра из приватной сети | `api` и `core` | — |
| Пароль Postgres | заявки с ПДн | Railway, служба `Postgres`; `EB_DB_DSN` у `api` | возможна утечка ПДн — решение об уведомлениях за оператором (`docs/privacy.md`) |

Если секрет попал в git: сначала ротация. Переписывание истории `main` запрещено (`AGENTS.md`), поэтому
отозванный ключ — единственная надёжная мера.

## Запрос на удаление ПДн

Человек просит удалить его данные. Подкоманда api по умолчанию только считает, удаляет — с `-yes`, одной
транзакцией (`backend/cmd/api/main.go`, `forget`; `docs/privacy.md`).

```bash
docker compose exec api /app/api forget -phone "+7 900 000-00-00"         # сколько найдётся
docker compose exec api /app/api forget -phone "+7 900 000-00-00" -yes    # удалить
docker compose exec api /app/api forget -code 3f9a1c07b2 -yes             # по номеру заявки
```

На Railway — та же команда в контейнере службы `api` (`railway ssh` в службу `api`).

Что удаляется по телефону: заявки с этим номером и записи, где номер есть в тексте (диалог заявки, вопросы журнала
ответов, оценки). Номер сравнивается по последним десяти цифрам. Вывод команды — только счётчики, без телефона и
имени.

Чего команда не находит и что сказать человеку:

- Имя без номера в свободном тексте — не найдётся (`docs/privacy.md`). Если человек назвал только имя — искать
  вручную под ролью владельца базы.
- История диалогов на стороне клиента лежит в `localStorage` его браузера (серверных сессий нет, T1) — удалить её
  может только он сам.
- Журналы служб и Prometheus ПДн не содержат; журнал расходов шлюза хранит только счётчики, без текстов
  (`store_prompts_in_spend_logs: false`).
- Тексты вопросов уходили провайдеру модели; что и сколько он хранит, этим репозиторием не управляется.
- Резервные копии Postgres на Railway — проверить вручную, в репозитории это не описано.

Остальное удалится само по сроку хранения (`EB_RETENTION_*`, по умолчанию 90 / 30 / 90 дней); удалённое видно в
метрике `eb_retention_deleted_total`.
