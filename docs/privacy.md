# Персональные данные стенда

Что считается персональными данными, где они лежат, сколько хранятся, как удалить по запросу и кто может
читать. Сроки по умолчанию — предложение команды, а не решение юриста: окончательные значения задаёт тот, кто
отвечает за обработку данных (оператор по 152-ФЗ), и они же должны совпасть с текстом согласия в форме заявки.

## Где лежат

| Где | Что персонального | Срок по умолчанию | Переменная |
|---|---|---|---|
| `leads` (Postgres стенда) | имя, телефон, компания, комментарий, диалог | 90 дней | `EB_RETENTION_LEADS_DAYS` |
| `answers` | вопрос клиента — в нём бывают имя и номер | 30 дней | `EB_RETENTION_ANSWERS_DAYS` |
| `feedback` | комментарий, вопрос и ответ | 90 дней | `EB_RETENTION_FEEDBACK_DAYS` |
| журнал расходов шлюза (`LiteLLM_SpendLogs`) | только счётчики, без текстов (`store_prompts_in_spend_logs: false`) | 30 дней | `llm-gateway/config.yaml` |
| журналы служб (stdout) | нет: тела запросов и контакты не пишутся | — | — |
| Prometheus | нет: только счётчики | 15 дней | `RETENTION` у службы prometheus |

Очистку по сроку делает Go-API в фоне раз в `EB_RETENTION_INTERVAL` (1 час): на нескольких репликах проход
выполняет одна (транзакционная блокировка в базе). Удалённое видно в метрике `eb_retention_deleted_total` и
в журнале api («очистка по сроку хранения»). В бою API не запустится с нулевым сроком — бессрочное хранение
противоречит ст. 5 ч. 7 152-ФЗ.

## Удаление по запросу человека

Человек просит удалить его данные (ст. 14, 21) — оператор запускает подкоманду api. По умолчанию она только
считает, удаляет — с `-yes`. Всё удаляется одной транзакцией.

```bash
docker compose exec api /app/api forget -phone "+7 900 123-45-67"         # что найдётся
docker compose exec api /app/api forget -phone "+7 900 123-45-67" -yes    # удалить
docker compose exec api /app/api forget -code 3f9a1c07b2 -yes             # по номеру заявки
```

На Railway — тем же бинарником в контейнере службы `api` (Railway CLI: `railway ssh` в службу `api`), команда та
же. По телефону удаляются заявки с этим номером и записи, где номер упомянут в тексте (диалог заявки, вопросы
журнала, оценки). Номер сравнивается по последним десяти цифрам: «8 900…» и «+7 (900)…» — один номер. Поиск в
свободном тексте — по цифрам подряд; имя в тексте без номера так не найдётся.

## Кто читает базу

`backend/scripts/sql/access.sql` заводит две роли (запуск — в шапке файла, вручную и один раз):

- `energytool_manager` — менеджер: таблица `leads` целиком, только чтение. Ему звонить клиенту.
- `energytool_analyst` — разбор качества: представления `analytics.answers` и `analytics.feedback` с телефонами
  и почтой, заменёнными метками, и `analytics.leads` — без контактов и диалога. К таблицам `public` доступа нет.

Служба api работает под владельцем базы и в эти роли не входит. Владельцу базы и администраторам Railway доступ
по-прежнему полный — это и есть круг лиц с доступом к ПДн, который нужно утвердить приказом оператора.

## Не сделано

- Шифрование телефона в колонке: менеджеру нужен номер в открытом виде, а ключ шифрования на том же сервере, что
  и база, защиту почти не добавляет. Защита — доступ к базе (роли выше) и шифрование диска на стороне хостинга.
- Учёт выдачи доступа и журнал обращений к `leads` (кто и когда читал) — средствами Postgres (`pgaudit`) на
  Railway недоступно; при переносе на свою инфраструктуру стоит включить.
- Текст согласия в форме заявки и срок в нём — на стороне фронта и оператора.
