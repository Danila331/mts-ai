## 0. Как пользоваться этим документом

- **Одна задача — одна ветка от `dev` — один PR в `dev`.** Имя ветки: `feature/<id>-<коротко>`, например `feature/t1-server-sessions`.
- Перед началом прочитай `AGENTS.md` (корень) и `web/AGENTS.md`. Если что-то расходится, они главнее этого файла.
- У каждой задачи есть: **Зачем** (критерий жюри), **Что сделать**, **Где** (файлы), **Готово, когда** (приёмка), **Не делать**.
- Номера миграций закреплены за задачами (раздел 5), чтобы параллельные ветки не конфликтовали.
- Закончил задачу — отметь её статус в разделе 6 этого файла в своём PR.

### Глобальные ограничения (нарушение = задача не принята)

1. **Факты о продуктах, ценах, сроках и порогах — только из `knowledge-base/`.** Никаких рублёвых расчётов экономии, тарифов и знаний модели. Числа из UI-логики (пороги, чек-листы) должны находиться в тексте базы, и это проверяет тест.
2. **Режим автопроверки (`solution.py`, `mode != "chat"`) не меняется.** Все новые фичи работают только в веб-режиме. После каждой задачи `scripts/check_submission.py` выдаёт 0 ошибок, а `eval/retrieval_eval.py --split dev` не ухудшается.
3. **Только тестовые персональные данные** («Тестов Тест Тестович», `+7 900 000-00-00`, «ООО Учебный склад»). В логах телефоны маскируются.
4. **Согласие на обработку ПДн оформляется на том же шаге, что и передача контактов** (`knowledge-base/00-reference/03-calculation-and-requests.md`, раздел «Согласие на обработку персональных данных»). Заявку нельзя создать без явного действия клиента.
5. **Нельзя обещать точное время звонка, имя специалиста или содержание разговора** (там же, раздел «Обратный звонок»). Поэтому запись в календарь «как у Qualified/Intercom» **запрещена**, вместо неё — предпочтение по времени (T4).
6. Секреты передаются только через env. Новые переменные добавляются в `.env.example` без значений и описываются в README.
7. Проверки перед PR:
   - Python: `.venv/bin/ruff check .`, `.venv/bin/python -m unittest discover -s tests`.
   - Go: `make -C backend lint test`, при изменении SQL — `make -C backend sqlc` и `make -C backend test-db`.
   - Web: `cd web && npm run lint && npx tsc --noEmit && npm run build`.
   - Сквозная: `docker compose up --build`, затем `sh backend/scripts/smoke.sh http://127.0.0.1:8787`.

## 2. Целевая демо-история (на неё работают все задачи)

> Клиент на сайте МТС → виджет приветствует по теме страницы (T8) → клиент загружает фото счёта (T9) → «Паспорт задачи» заполняется сам (T2) → бот ведёт к нужному продукту с источниками → предлагает передать менеджеру → карточка заявки прямо в чате, согласие одним кликом (T2) → заявка получает оценку «горячая» с причинами (T3) → **в Telegram менеджера приходит карточка** (T5) → менеджер открывает `/manager`: паспорт, резюме, расшифровка, «что спросить» → экспорт в CRM (T5). Клиент скачивает «Итоги консультации» (T10).

## 3. Задачи

Приоритет: **P0** — без этого рискуем допуском и «Работоспособностью»; **P1** — основная ценность для бизнеса; **P2** — «вау» для клиента; **P3** — техническая глубина.

### T1 · P0 · Серверные сессии и полная история

**Зачем:** пункт 5 кейса, «Работоспособность» (30%). Это фундамент для T2–T5 и T11.

**Что сделать**
- Миграция `000002_sessions`: таблица `sessions`:
  - `id text pk` — id сессии фронта;
  - `channel text` — `playground | embed | telegram`;
  - `mode text`;
  - `title text`;
  - `page jsonb` — url, title, utm; заполняется в T8;
  - `created_at`, `updated_at`.
- В той же миграции: колонки `answers.session_id text NULL` с индексом `(session_id, created_at)` и `answers.sources jsonb` — id разделов базы из `citations`, без текста.
- В `answers` сохраняй **и реплику клиента, и ответ**. Сначала проверь, что сейчас лежит в `answers.question`: последняя реплика или весь диалог. Нужна последняя реплика.
- `POST /api/chat` принимает `session_id` и `channel` (поля опциональны для обратной совместимости). Сессия создаётся upsert-ом на первом сообщении.
- «Новый диалог» на фронте уже создаёт новый id: проверь, что он уходит в API, а старая сессия остаётся на сервере.
- `GET /api/sessions/:id` (только с менеджерским токеном, см. T5) отдаёт сессию и реплики по порядку.
- `localStorage` остаётся кэшем UI. Источник истины для менеджера — сервер.

**Где:** `backend/migrations/`, `backend/queries/`, `backend/internal/chat/usecase/service.go`, `backend/internal/transport/http/handlers.go`, `web/src/lib/api.ts`, `web/src/hooks/use-chat.ts`.

**Готово, когда**
- Диалог из виджета без заявки виден в базе целиком (SQL или `GET /api/sessions/:id`) после очистки `localStorage`.
- «Новый диалог» создаёт новую строку `sessions`; модель новой сессии не видит прошлых реплик (тест в `api_test.go`).
- `smoke.sh` проверяет: два сообщения с одним `session_id` → в базе одна сессия и две пары реплик.

**Не делать:** не хранить промпт и выдачу поиска (решение из `000001`: это десятки КБ на ответ).

### T2 · P0/P1 · «Паспорт задачи» и заявка прямо в чате

**Зачем:** закрывает D2. «Ценность для бизнеса» (25%) — менеджер получает структурированные данные, а не пересказ. Конкуренты (Fin, Breeze, BitrixGPT) делают то же, но **скрыто от клиента**. Наше отличие — паспорт виден клиенту, его можно поправить, и это повышает доверие.

**Поля паспорта.** Берутся из базы, раздел «Какие сведения могут понадобиться» (`00-reference/03-calculation-and-requests.md`) и «Параметры, влияющие на подбор решения» (`00-reference/00-product-map.md`):
- общие: `org_type`, `object_type`, `region`, `task` (`снижение платежа | автоматизация учёта | поиск потерь | надёжность электроснабжения`), `connected_power`, `monthly_consumption`, `metering` (приборы и способ сбора);
- по продуктам — подсписки из того же раздела базы (ОРЭМ, СЭС, платформа учёта, потери, распознавание по фото);
- контакты: `name`, `phone`, `company`, `callback_preference` (T4);
- `product_candidates[]` — какие продукты обсуждались, с id разделов базы.

**Что сделать**
- **Извлечение.** После события `answer` в режиме `chat` бэкенд асинхронно вызывает модель с JSON-схемой паспорта по всему диалогу. Затем отправляет SSE-событие `passport` **до** `done`: клиент уже видит ответ, задержка не ощущается.
  - Правило промпта извлечения: «только то, что клиент сказал сам; если не сказал — `null`». Утверждения ассистента — не данные клиента.
  - Телефон валидируется в Go детерминированно: RU, 10–11 цифр, нормализация в `+7XXXXXXXXXX`.
  - При сбое модели паспорт не меняется, ответ не теряется.
- Миграция `000003_passport`: `sessions.passport jsonb`; `leads.session_id text`, `leads.passport jsonb`.
- **UI стенда (`/playground`):** правая карточка «Паспорт задачи». Поля, которые заполнил бот, подсвечиваются на 1,5 с. Любое поле можно править (`PATCH /api/sessions/:id/passport`). Прогресс — «заполнено N из M для <продукт>».
- **UI виджета (`/embed`):** компактная полоса «Что я понял о задаче · N полей», разворачивается.
- **Заявка в чате.** Когда в паспорте есть имя, телефон и компания, **или** клиент согласился на передачу, под сообщением бота появляется inline-карточка «Проверьте заявку». В ней предзаполненные поля, **чекбокс согласия на обработку ПДн на этом же шаге** и кнопка «Отправить». `POST /api/lead` принимает `session_id` и берёт паспорт с сервера.
- Обнови `CHAT_MODE` в `energybot/prompts.py`: на согласие клиента бот одной фразой просит контакты и говорит, что ниже откроется форма для проверки. Бот не утверждает, что заявка отправлена, — это делает только UI после ответа API.
- Старая модальная форма остаётся как запасной путь (кнопка «Передать менеджеру»).

**Где:** `backend/internal/lead/`, новый пакет `backend/internal/passport/` (схема, промпт извлечения, нормализация телефона), `backend/internal/chat/usecase/`, `web/src/components/chat/` (новые `passport-card.tsx`, `inline-lead.tsx`), `web/src/hooks/use-chat.ts`, `energybot/prompts.py` (только `CHAT_MODE`).

**Готово, когда**
- Сценарий из демо-вопроса 18 («три склада, ~40 счётчиков, не готов оставлять телефон»): паспорт содержит объекты и число приборов, контактов нет, заявка **не** создаётся, консультация продолжается.
- Клиент пишет в чат «Тестов Тест, +7 900 000 00 00, ООО Учебный склад» → появляется inline-карточка с этими полями → без чекбокса кнопка неактивна → после отправки заявка в `leads` с `session_id` и паспортом.
- Go-тесты: нормализация телефона (10 вариантов записи), извлечение не пишет данные из реплик ассистента (мок модели), сбой извлечения не роняет чат.
- В автопроверке ничего не изменилось: `check_submission.py` = 0 ошибок, `CHAT_MODE` не попадает в промпт при `mode != "chat"` (тест есть или добавлен).

**Не делать:** не отправлять заявку автоматически без клика; не показывать в паспорте поля, которых нет в чек-листах базы.

### T3 · P1 · Скоринг заявки с объяснением

**Зачем:** закрывает D4. Делает «качественные заявки» измеримыми — это аргумент для 25% «ценности».

**Что сделать**
- **Детерминированные правила, не LLM.** Скоринг должен быть объяснимым и воспроизводимым. Пакет `backend/internal/lead/score/`.
  - **Соответствие (fit):** определён продукт, и паспорт не противоречит границам из `00-reference/02-product-scope-and-limits.md`.
  - **Полнота:** доля заполненных полей чек-листа нужного продукта из T2.
  - **Намерение:** клиент спрашивал про расчёт, стоимость или сроки, согласился на звонок, назвал объём.
  - **Минусы:** вопрос вне тематики, явное «просто интересуюсь».
- Результат: `{"grade": "hot|warm|cold", "points": 0..100, "reasons": ["Подходит: выход на ОРЭМ", "Заполнено 5 из 6 полей", ...], "missing": ["класс напряжения", ...]}`.
- Миграция `000004_lead_score`: `leads.score jsonb`.
- `missing` — это «что спросить менеджеру на звонке». Вывод в `/manager` (T5) и в резюме.
- Резюме (`SummarySystem`) расширить до структурированного блока: задача, объект, подходящий продукт, **известные параметры паспорта**, что уточнить. Правило «ничего не додумывай» сохраняется.

**Готово, когда**
- Табличный Go-тест: 8 синтетических паспортов → ожидаемые grade и reasons.
- Каждое правило ссылается в коде на раздел базы (комментарий с путём и заголовком раздела).
- В UI и презентации **нет заявлений о росте конверсии**: данных об этом нет.

### T5 · P1 · Рабочее место менеджера `/manager`, уведомления, экспорт

**Зачем:** закрывает D3. Пункт 8 кейса, «Сценарий внедрения» (15%), демо-момент «у жюри пиликает Telegram».

**Что сделать**
- **Доступ.** `EB_MANAGER_TOKEN` (env). Вход по токену, httpOnly-cookie на стороне Next, токен не попадает в клиентский JS. Все `GET /api/manager/*` закрыты им.
- **`/manager` — входящие заявки:**
  - таблица: номер, время, grade (T3), продукт, компания, полнота паспорта;
  - фильтры по grade, продукту, «без заявки»;
  - вкладка «Все диалоги» — сессии без заявки (T1).
- **`/manager/leads/:code` — карточка заявки:**
  - паспорт (T2), score и reasons, блок «Что спросить на звонке» (`missing`);
  - резюме, расшифровка диалога;
  - у каждого ответа бота — ссылки на разделы базы из `answers.sources` (T1) → `/kb?chunk=`;
  - статус заявки: `new | in_progress | done | rejected` — миграция `000005_lead_status`.
- **Telegram-уведомление.** `EB_TG_BOT_TOKEN`, `EB_TG_CHAT_ID`; если не заданы — выключено. Отправка в горутине с ретраями, не блокирует ответ клиенту. Сообщение: grade-эмодзи, продукт, компания, 2 строки резюме, ссылка на карточку. **Телефон в Telegram маскируется**, полный — только в `/manager`.
- **Webhook в CRM.** `EB_LEAD_WEBHOOK_URL` + `EB_LEAD_WEBHOOK_SECRET`. POST JSON с подписью `X-EB-Signature: sha256=<HMAC>`, ретраи с backoff, журнал доставок в таблице `lead_deliveries`.
- **Документ `docs/integration.md`:** схема payload, маппинг полей на amoCRM (сделка + контакт + примечание) и Битрикс24 (лид, `crm.lead.add`). Реальная интеграция с CRM МТС не требуется (база: «Интеграции с CRM, сайтом или почтой не требуются»). Показываем готовый контракт.
- Экспорт CSV из списка заявок.

**Готово, когда**
- Заявка из виджета появляется в `/manager` без перезагрузки (поллинг 10 с или SSE).
- Без токена `/api/manager/*` → 401 (тест).
- Webhook на локальный тестовый приёмник: подпись проверяется, повторная доставка идемпотентна по `lead.code`.
- Telegram выключен без env, сбой Telegram не влияет на `POST /api/lead` (тест с моком).

### T6 · P1 · Аналитика воронки и пробелов базы (`/manager/analytics`)

**Зачем:** «Скорость и стабильность» (15%) и «ценность для бизнеса». Это аналог Topics Explorer у Intercom Fin и Suggestions у Tidio. Команда EnergyTool сама проводит CJM-исследования — это их язык.

**Что сделать**
- **Воронка по `sessions`/`answers`/`leads`:** сессии → ≥2 реплики клиента → бот предложил заявку → заявка. Срезы по каналу и странице (T8).
- **Скорость:** p50/p95 полного ответа и этапов из `answers.timings`, доля `fallback`, доля срабатываний guard.
- **«Вопросы без ответа»:** ответы с `fallback`, со срабатыванием guard или с фразой о том, что в материалах нет ответа. Список с группировкой похожих (пересечение основ слов, без LLM) → кнопка «скопировать для команды контента».
- **👎 с комментариями** из `feedback`.

**Готово, когда** на синтетических данных (seed-скрипт `backend/scripts/seed_demo.sql` с тестовыми сессиями) все графики рисуются, а SQL-запросы покрыты `test-db`.

### T7 · P2 · «Энергодиагностика за 60 секунд» (мастер)

**Зачем:** у конкурентов статичные калькуляторы (Time2Save, eesave, яЭнергетик). У нас — **детерминированный маршрутизатор по правилам базы** с источниками и сразу в диалог.

**Что сделать**
- Кнопка в пустом чате и в виджете: «Подобрать решение за 5 вопросов». Шаги: тип организации → задача → присоединённая мощность (диапазоны) → как сейчас собираются показания → регион.
- Ответы сразу пишутся в паспорт (T2).
- Результат: 1–2 направления с объяснением «почему» и ссылками на разделы базы. Пример: пороги мощности из `10-energy/12-power-thresholds.md` для ОРЭМ. Затем кнопка «Продолжить в чате».
- Правила живут в одном файле `web/src/lib/diagnostic-rules.ts`. **Тест:** каждое число и каждый id раздела в правилах существует в тексте базы (аналог `eval/validate_dataset.py`).

**Не делать:** никаких рублей, процентов экономии и окупаемости. Только «какое направление подходит и почему, по базе».

### T8 · P2 · Виджет, который знает страницу

**Зачем:** проактивность как у Qualified и Drift, но без навязчивости. «Сценарий внедрения».

**Что сделать**
- `widget/loader.ts` передаёт в iframe `location.pathname`, `document.title`, UTM-метки (только эти поля, без cookies).
- Новый атрибут `data-topics='{"/solar":"solar","/askue":"askue"}'`. Под каждую тему — своё приветствие и быстрые вопросы, по умолчанию — текущие.
- Страница пишется в `sessions.page` (T1) для аналитики (T6).
- **В промпт страница не попадает как факт.** Допустимо только как подсказка поиску (буст документа продукта): отдельный флаг `EB_PAGE_BOOST`, выключен по умолчанию, включать только после замера `retrieval_eval`.
- Обновить `/widget` (настройки + превью) и `DESIGN.md` (протокол встраивания).

### T9 · P2 · Счёт или договор по фото/PDF → паспорт

**Зачем:** «вау» для клиента. Для юрлиц в РФ аналогов не нашли.

**Что сделать**
- Кнопка-скрепка в поле ввода (стенд и виджет). PDF — извлечение текста; фото — vision-модель через `EB_VISION_MODEL` (OpenAI-совместимый `/chat/completions` с `image_url`). Если переменная не задана, **кнопка скрыта**.
- Извлекаются **только данные клиента** (ценовая категория, присоединённая мощность, класс напряжения, объём потребления, поставщик, регион) → предложение «Я нашёл в документе: … Добавить в паспорт?» → клиент подтверждает.
- Файл обрабатывается в памяти и **не сохраняется**. В `answers` пишется только факт загрузки и извлечённые поля. Лимит 10 МБ, типы `pdf/jpg/png/heic`.
- Модуль не импортируется `solution.py` и не попадает в ZIP: зависимости сабмита не меняются.

**Готово, когда** на 3 синтетических счетах (сгенерированных, без реальных реквизитов; лежат в `tests/fixtures/`) поля извлекаются, клиент видит их до записи в паспорт, а без `EB_VISION_MODEL` UI не показывает кнопку.

### T10 · P2 · «Итоги консультации» для клиента (PDF)

**Зачем:** в B2B решение принимает не один человек: энергетик пересылает документ директору. Среди найденных аналогов такого нет. «Ценность для клиента».

**Что сделать**
- Страница `/report/:sessionId` с print-CSS → «Скачать PDF» через `window.print()`, без серверных зависимостей.
- Содержание:
  - задача и паспорт;
  - обсуждённые продукты — каждый с 1–2 фактами **дословно из ответов бота** и ссылками на разделы базы;
  - чек-лист «Что подготовить для расчёта» — из раздела базы «Какие сведения могут понадобиться» под продукт;
  - оговорка из базы: предварительная оценка «не является коммерческим предложением».
- Доступ по секретному id сессии (тот же подход, что в T1). Кнопка в чате после 3+ реплик.

**Не делать:** новый текст от модели в отчёте. Только сохранённые ответы, паспорт и цитаты базы.

### T11 · P3 · Режим «Копилот менеджера МТС»

**Зачем:** пятая аудитория кейса («региональные менеджеры МТС, продающие B2B-решения»). Её **никто** из аналогов не закрывает.

**Что сделать**
- Новый `mode="copilot"` в `energybot/prompts.py`. Те же правила «только база», но:
  - ответ длиннее (до 150 слов);
  - формат «коротко / детали / источники»;
  - сценарии «сравни продукты», «черновик письма клиенту», «ответ на возражение».
- Доступ — из `/manager` (вкладка «Спросить базу»).
- Опционально: Telegram-бот на том же ядре (`channel=telegram`), только для тестового чата.
- Режимы `chat` и автопроверки не меняются. Добавь тест, что `copilot`-правила не попадают в их промпт.

### T12 · P3 · Уверенность и отказ ниже порога

**Зачем:** кейс прямо предлагает «если уверенность ниже порога — уточняющий вопрос». «Обоснованность техрешений» (20%).

**Что сделать**
- В ядре — метрика уверенности из скоров реранкера/RRF и доли опоры. Показ в отладке: шкала и порог.
- Маршрут `clarify` ниже порога — **только в режиме `chat`** под флагом `EB_CONFIDENCE_GATE`.
- Порог калибруется на `eval` dev. Включение в автопроверке — отдельное решение после `run_eval --with-demo --baseline` с цифрами «до/после» в PR (правило из `AGENTS.md`).

### T13 · P3 · Потоковая выдача токенов

**Зачем:** «Скорость» (15%): воспринимаемая задержка.

**Что сделать**
- SSE-события `delta` из ядра → Go пересылает как есть → фронт печатает текст.
- Guard работает по завершении. Если он переписал или вырезал предложение, финальное событие `answer` заменяет текст, а в UI появляется метка «Уточнено проверкой».
- Замерить время до первого токена и полное время до/после, приложить к PR.
- В виджете можно оставить потоковую выдачу выключенной (`data-stream="0"`), если правки guard на глазах клиента выглядят плохо. Решение — по скриншотам в PR.

### T14 · P3 · Стенд «Стресс-тест» по персонам

**Зачем:** аналог Fin Simulations и Ada Simulations. Показывает жюри, что качество измеряется, а не декларируется.

**Что сделать**
- Скрипт `eval/personas.py`: 5 персон из кейса (МСБ, энергетик, СНТ, сетевая компания, менеджер МТС) × N сценариев → многоходовые диалоги с ботом. Метрики:
  - доля ответов без чисел вне базы (guard);
  - задан ли уточняющий вопрос;
  - предложена ли заявка в нужный момент;
  - заполнение паспорта.
- Результат — JSON. Страница `/lab` в стенде показывает последний закоммиченный отчёт (без текстов базы).
- **Прогоны платные: только с разрешения владельца ядра.**

## 4. Чего НЕ делать (решения приняты)

| Идея | Почему нет |
|---|---|
| Калькулятор экономии в рублях, окупаемость, сравнение ЦК в деньгах | Тарифов в базе нет, а база запрещает собственные расчёты. Нарушение ограничения №2 кейса убивает главный козырь — проверяемость |
| Запись в календарь на конкретное время | База запрещает обещать точное время звонка → T4 |
| 3D-крыша и спутник для СЭС | Долго делать, и обосновать нечем |
| Деанонимизация компании посетителя, трекинг | ПДн и доверие, кейс этого не требует |
| Автоматический дожим (email или мессенджер) без согласия | Без явного согласия клиента — нет |
| Голосовой агент | Только диктовка в поле ввода (Web Speech API), и только если останется время |

|---|---|
| `000002_sessions` | T1 |

- **Волна 4:** T12, T14 (нужны ключи модели и разрешение на платные прогоны).

**Если до сдачи меньше суток:** только T1 + T2 (+ упрощённый T5: список заявок и Telegram). Остальное — слайд «Дорожная карта» в презентации со ссылкой на этот файл.
