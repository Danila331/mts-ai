### 2.1 Счастливый путь: учёт на трёх складах — 1:30

Реплики взяты из демо-вопроса 18 (`demo_questions.csv`). Вводим по одной:

1. «Хотим понять, сколько будет стоить автоматический учёт на наших объектах.»
   Ожидаем: стоимость зависит от числа приборов и конфигурации, и бот задаёт один уточняющий вопрос об объектах.
2. «Три склада, всего около сорока счётчиков.»
3. «Я пока не готов оставлять телефон. Можете объяснить, что понадобится для оценки?»
   Ожидаем (эталон 18): телефон не нужен. Для оценки — модели и количество приборов по объектам, как сейчас
   собираются показания и какую задачу решаем. В конце один вопрос. **Бот не настаивает на контактах.**

Показываем (говорит ядро/RAG):
- номер источника после предложения → клик → превью раздела → ссылка `/kb?chunk=<id>`: «каждое утверждение
  проверяется по базе»;
- «Отладка ответа»: вкладка «Поиск» (что нашлось и с каким рангом), «Опора», «Проверка» (guard: числа только из

### 2.5 «Честные нет» — отдельный слайд, демо 0:30 (T26)

Текст слайда:

> **Честно: не подойдёт.** Если по словам клиента продукт ему не подходит по условию из базы знаний, бот прямо
> говорит «вам это, скорее всего, не подойдёт, потому что…», даёт ссылку на раздел базы и предлагает то, что
> подходит. Для пресейла это звонки, на которые не придётся тратить время.
>
> - 15 правил, каждое — условие базы дословно, раздел и детектор по словам клиента (`scripts/honest_no.py`).
> - Не категоричнее базы: где база говорит «может» (газ и тепло в распознавании, станция больше 500 кВт), правила
>   нет. Оговорка базы входит в причину («исключение возможно, если…»).
> - Без данных бот не отговаривает: мощность не названа или названа как «больше 500 кВт», площадок несколько,
>   у шифера не указан возраст.
> - Тест сверяет каждую причину, альтернативу и порог с текстом базы. Автопроверка этот блок не видит.

Реплики для демо. Каждую вводим в новом диалоге в `/playground`. Под ответом появляется плашка «Честно: не
подойдёт». Клик по «Основание» открывает раздел базы.

| Реплика | Плашка: почему (дословно из базы) | Что подойдёт | Контроль: плашки нет |

| «Мы энергосбыт, нужен поиск хищений» | Потери несут сетевые организации, а не сбытовые; исключение — сетевые организации на балансе (`24-losses.md`, «Не подходит энергосбытовым компаниям») | платформа учёта, распознавание показаний по фото (`20-portfolio.md`, «Энергосбытовая компания») | «Мы энергосбыт, у нас на балансе сетевые организации, интересует поиск потерь» |
| «Хотим выйти на оптовый рынок, присоединённая мощность 450 кВт» | Ниже 750 кВт выход невозможен, это регуляторное ограничение (`21-orem.md`, «Порог доступа…») | анализ ценовой категории, солнечная станция, платформа учёта (`20-portfolio.md`, «Промышленное предприятие») | «… присоединённая мощность 1,2 МВт» или «… больше 500 кВт» |

Не говорим: «бот никогда не ошибётся» или «сэкономит N часов». Замеров нет. Пометки «клиенту объяснено, почему не

## 3. Архитектура, ADR и замеры — 1:30

Слайд со схемой из README:

```
браузер ──▶ web (Next) ──▶ api (Go) ──▶ core (Python, energybot/) ──▶ llm-gateway (LiteLLM) ──▶ провайдер модели
                             ├─▶ Postgres (заявки, журнал)   ├─▶ Redis (пределы частоты)   └─▶ Prometheus
```

- Одно ядро `energybot/` на автопроверку (`solution.py`) и на веб-чат, поэтому ответы не расходятся.
- Поиск: BM25 + `bge-m3` через RRF, затем реранкер Qwen3. Guard по числам. Ступени деградируют: без эмбеддингов
  работает BM25, без реранкера — RRF, без LLM — выдержка из базы.
- Ключ провайдера знает только шлюз. Ядро в приватной сети. Пределы частоты, сроки хранения ПДн, 7 правил тревог.
- ADR (RAG вместо fine-tuning, гибридный поиск, разделение Go и Python) — `docs/architecture/` (T33, в работе).
  Если к защите не готово, говорим решения устно по [`QA.md`](QA.md), вопросы 3 и Д3.

## 4. Экономика — 1:30

Рублей и тарифов не называем: база запрещает собственные расчёты, а замера у нас нет.

- Логика ценности: бот квалифицирует, а человек закрывает сделку. Менеджер получает резюме вместо голого
  телефона, и на звонке ему не надо выяснять задачу заново.
- Модель эффекта (T41) — воронка без конкретных чисел: визиты × доля открывших чат × доля дошедших до заявки ×
  доля целевых. Каждый параметр будет задан диапазоном с источником и уровнем уверенности; реальные значения даст
  пилот.
- Стоимость диалога: замера нет. Шлюз уже считает токены и расход по службам (`llm-gateway/README.md`), токены
  на каждый ответ в журнале — T34. Скажем так: «цифру покажет пилот на реальных диалогах».
- Внешние опоры с пометкой: HBR 2011 (старые данные США); Gartner 2026 — 69% B2B-покупателей перепроверяют
  выводы ИИ у продавца, это аргумент за человека в контуре (приложение B ROADMAP).
- «~400 тыс. компаний» из ROADMAP T41 — только как объём рынка, на конверсии не умножаем. Источник этой цифры
  перед защитой сверить с `МТС_кейс.pdf`.

## 5. Внедрение — 1:30

- **Заявки:** сейчас в Postgres, менеджер читает их под ролью `energytool_manager`. Дальше — `/manager`, Telegram

- **Пилот (T40, `docs/rollout.md` в работе):** офлайн-оценка → shadow-режим → 5–10% трафика → A/B против формы →

- **Человек в контуре:** передача менеджеру по запросу клиента; вопросы о цене и договоре — к специалисту.
- **Обновление базы:** Markdown → валидатор выборки и `retrieval_eval` → перевыкатка ядра.

## 6. Что не сделано и почему мы — 1:00

Не сделано (статусы — ROADMAP, раздел 6): серверные сессии (T1), паспорт и заявка в чате с чекбоксом согласия (T2),
скоринг (T3), экран менеджера и уведомления (T5), потоковая выдача (T13), нагрузочный тест (T32), red-team набор
(T35). Причина одна: сначала мы сделали проверяемое качество ответа и допуск, потом продажную обвязку.

Почему мы:
1. Каждый факт проверяется: номер источника ведёт в раздел базы, а проверка ответа режет выдуманные числа.
2. Мы измеряем, а не обещаем: 500 кейсов по всей базе, слепой судья по методике платформы, свои слабые места
   названы цифрами.
3. Стенд поднимается одной командой, встраивается одной строкой, модель меняется в шлюзе без правки кода.

## Целевая история: когда будут T1/T2/T3/T5/T8/T9/T10

Сейчас этого **нет** в стенде. На защите рассказываем как план и не показываем как готовое.

| Шаг целевой истории (ROADMAP, раздел 2) | Задача | Что есть сейчас вместо этого |
|---|---|---|
| Виджет приветствует по теме страницы | T8 | одно общее приветствие и быстрые вопросы из настроек виджета |
| Клиент загружает фото счёта | T9 | нет; клиент пишет данные текстом |
| «Паспорт задачи» заполняется сам, виден клиенту | T2 | нет; данные клиента есть только в диалоге и в резюме заявки |
| Заявка карточкой прямо в чате, согласие одним кликом | T2 | модальная форма «Передать запрос менеджеру», чекбокса согласия нет |
| Оценка «горячая» с причинами | T3 | нет |
| Карточка в Telegram менеджера | T5 | нет |
| `/manager`: паспорт, резюме, расшифровка, «что спросить», экспорт в CRM | T5 | заявка в Postgres, запрос из README |
| Серверная история всех диалогов, включая разговоры без заявки | T1 | история в `localStorage` браузера |
| Клиент скачивает «Итоги консультации» (PDF) | T10 | нет |

Как прозвучит демо, когда задачи будут готовы. Клиент открывает страницу продукта, и виджет предлагает вопрос
по теме (T8). Клиент прикладывает фото счёта, бот переписывает из него ценовую категорию и мощность и просит
подтвердить (T9). Справа заполняется паспорт (T2). Бот ведёт к продукту с источниками, предлагает менеджера, и в
чате появляется карточка заявки с чекбоксом согласия (T2). Заявка получает оценку и причины (T3). В Telegram
менеджера приходит карточка с замаскированным телефоном, а в `/manager` есть резюме, расшифровка и «что
спросить» (T5). Клиент скачивает PDF с итогами для директора (T10).
