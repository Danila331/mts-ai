# Плейбук внедрения и пилота

Как довести консультанта от стенда до сайта EnergyTool: этапы, метрики, условия остановки, человек в контуре,
владельцы, обновление базы, встраивание и план первых 30 дней. Документ закрывает задачу T40 и критерий финала
«Сценарий внедрения» (15%, [`ROADMAP.md`](ROADMAP.md), раздел 1).

Это план. Что уже есть в коде, а что появится в задачах роадмапа, отмечено в каждой таблице.

**Правила документа**

- Любое число либо взято из репозитория (указано откуда), либо помечено **[предложение]**. Такое значение
  предложила команда, его уточняют на shadow и пилоте. Это не данные.
- Эффект (рост конверсии, экономия) не заявляем: его измеряет пилот ([`ROADMAP.md`](ROADMAP.md), раздел 7,
  тезис 8). Модель экономики — в задаче T41.
- Клиенту не обещаем точное время звонка, имя специалиста и содержание разговора
  (`knowledge-base/00-reference/03-calculation-and-requests.md`, раздел «Обратный звонок»; глобальное
  ограничение 5 в роадмапе).
- Вне скоупа по решению владельца от 15.11.2026: 152-ФЗ в полном объёме, окружение МТС (MWS, Exolve),
  любые запросы к energytool.mts.ru. Базовая гигиена ПДн уже сделана — [`privacy.md`](privacy.md).

## 0. Что решаем не мы

Без этих решений пилот на реальном трафике не стартует. Команда их не проектирует, но называет.

| Решение | Кто принимает | Почему важно |
|---|---|---|
| Можно ли обрабатывать реальные ПДн на текущем хостинге: Vercel + Railway, регион EU West ([`deploy.md`](deploy.md)) | оператор ПДн и ИБ МТС | Перенос в контур МТС вне скоупа. Пока решения нет, shadow идёт только на обезличенных вопросах |
| Сроки хранения `EB_RETENTION_*` и текст согласия | оператор ПДн | Значения по умолчанию 90 / 30 / 90 дней — предложение команды ([`privacy.md`](privacy.md)) |

| Базовые цифры текущей формы: заявки на визит, доля целевых | продукт и аналитика МТС | Без базы A/B не с чем сравнивать, а размер выборки не посчитать |
| Продукт и страницы для пилота | продукт | Нужны страницы с текущей формой и трафиком, достаточным для A/B |

### 1. Офлайн-оценка

| Что | Чем | Критерий |
|---|---|---|
| Выборка корректна | `eval/validate_dataset.py eval/dataset/parts/*.jsonl`, затем `eval/build_dataset.py` | 0 ошибок. ~500 кейсов, деление dev/holdout 70/30 ([`README.md`](../README.md)) |
| Поиск | `eval/retrieval_eval.py --split dev` (работает без ключей) | Не хуже последнего замера в docs/development.md (BM25: все разделы эталона в контексте — 0.63, доля найденных — 0.77) |
| Ответы | `eval/run_eval.py --with-demo --baseline`; слепой судья — `eval/blind_judge.py`, `eval/codex_judge.py` | Score не ниже последнего прогона на той же модели. В README от 09.11.2026: 0.896 на всём наборе, 0.806 на демо |
| Ловушки и вне базы | `must` / `must_not` в отчёте `run_eval`, категории `trap`, `out-of-kb`, `adversarial` | Не хуже прошлого прогона. Вопросы вне базы — известное слабое место (0.67 в README) |
| Сабмит не сломан | `scripts/check_submission.py` | 0 непройденных проверок |

Ограничение: `run_eval` проверяет режим автопроверки (`solution.py`): один ответ, без `CHAT_MODE` и без заявки.
Режим `chat` проверяется на shadow. Многоходовые диалоги по персонам появятся в задаче T14 (`eval/personas.py`).

### 2. Shadow

- **Как устроено.** Боевого shadow (бот молча отвечает рядом с формой сайта) нет: для него нужна интеграция с
  сайтом, а это вне скоупа. Пресейл вводит обезличенные вопросы клиентов (из текущих форм и звонков) в
  `/playground` в режиме «Чат». Он видит отладку («Опора», «Проверка»), ставит 👍/👎 с комментарием, оценки
  попадают в `feedback`. Глобальные настройки RAG на стенде закрыты токеном администратора (T29, сделано).
- **Разметка ошибок:** выдуманный факт или число; обещание цены, срока или звонка; неверный продукт; лишний
  или пропущенный уточняющий вопрос; заявка предложена не вовремя.
- **Ошибки идут в «золотой» набор.** Каждый подтверждённый промах контент-команда и пресейл оформляют кейсом в
  `eval/dataset/parts/*.jsonl` по [`eval/dataset/SPEC.md`](../eval/dataset/SPEC.md). Так shadow пополняет
  офлайн-регрессию.
- **Выход:** не меньше 200 размеченных ответов **[предложение]**. Измерены доля 👎 и доля ответов со
  срабатыванием guard или запасным ответом: это база для порогов раздела 3. Ошибок «обещание цены, срока или
  звонка» нет, либо каждая исправлена и закрыта регрессионным кейсом. Пресейл утвердил критерии целевой заявки
  (вход для T3) и формат резюме (`SummarySystem` в `backend/internal/lead/lead.go`).

### 3. Пилот на 5–10% трафика

- **Как устроено.** Тег виджета стоит на страницах одного продукта. Показ доле посетителей обеспечивает сайт:
  5% **[предложение]** на старте, 10% после недели без срабатываний условий остановки. Заявки пишутся в
  Postgres (`leads`).
- **Блокеры в коде** (без них метрики пилота не посчитать или виджет нельзя ставить на чужой домен):

| Задача | Зачем пилоту |
|---|---|
| T1 — серверные сессии | Отделить трафик виджета (`sessions.channel`) от стенда и жюри; видеть диалоги без заявки |
| T2 — паспорт задачи | Метрика полноты паспорта, `leads.session_id` |
| T5 — `/manager`, статусы, уведомление, webhook | Разметка целевых заявок статусами; пресейл видит заявки без SQL |
| T35 — защита виджета | `frame-ancestors` по allowlist `EB_EMBED_ALLOWED_ORIGINS`, проверка postMessage, honeypot на заявке. Сейчас этих заголовков в `web/next.config.ts` нет |
| T34 — `answers.usage` | Стоимость диалога |
| T33 — runbook | «Модель недоступна», «всплеск 429», «переиндексация и откат», «утечка ключа», «запрос на удаление ПДн» |

- **Дежурство.** Доставки тревог пока нет: правила `monitoring/rules.yml` видны только во вкладке Alerts
  Prometheus. Alertmanager или Grafana с отправкой в Telegram — бэклог T34. До этого дежурный смотрит Alerts
  по расписанию **[предложение: дважды в рабочий день]**.

### 4. A/B «чат против текущей формы»

- **Группы.** A — страница как есть, с формой. B — та же страница с виджетом. Форма в B остаётся: убирать
  рабочий канал на пилоте рискованно. Посетитель закрепляется за группой на стороне сайта.
- **Главная метрика** — целевые заявки на визит **по странице целиком** (форма + чат). Если мерить только
  заявки чата, чат может просто перетянуть их у формы, и рост окажется ложным.
- **Вторичные метрики** — все заявки на визит, полнота паспорта, время уточняющего звонка. **Ограничители** —
  CSAT, p95 задержки, стоимость диалога, жалобы (раздел 2).
- **Размер выборки** считается до старта, по базовой конверсии формы `p` (её даёт МТС) и минимальному эффекту
  `δ`, который продукт считает значимым. Оценка — правило Лера: `n ≈ 16·p(1−p)/δ²` на группу (α = 0,05
  двусторонний, мощность 80%). Длительность = `n` / визиты в группу за день, но не меньше 2 полных недель
  **[предложение]**: у B2B-трафика недельный цикл. Итог подводим в заранее назначенную дату, без
  подглядывания.
- **Откуда данные.** Заявки формы уходят в CRM МТС, нашей системе они не видны. Сравнение собирает аналитика
  МТС: выгрузка формы плюс наши `leads` (CSV или webhook из T5). Метка группы приходит в UTM-параметрах страницы
  и пишется в `sessions.page` (T1, T8). Пресейл размечает заявки обеих групп по одним критериям и по
  возможности не знает группу.

### 5. Масштабирование

- Порядок: следующий продукт → остальные продукты → регионы. Каждый продукт проходит короткий цикл: офлайн-прогон
  `run_eval --filter` по его области → неделя shadow **[предложение]** → пилот.
- Тема и приветствие под страницу — атрибут `data-topics` (T8).
- Перед ростом трафика: нагрузочный замер k6 (T32). Пересмотр пределов ключей шлюза: сейчас 240 и 60 запросов
  в минуту для ядра и api, 16 и 4 одновременных (`GW_KEY_*_RPM`, `GW_KEY_*_PARALLEL`, [`deploy.md`](deploy.md)).
  Потолок расхода — `GW_KEY_*_BUDGET`. Пределы частоты api уже общие для всех реплик (Redis).

## 2. Метрики пилота

| Метрика | Как считается | Что есть сейчас | Что появится, задача |
|---|---|---|---|
| Заявки на визит | Заявки со страниц пилота / визиты этих страниц | Числитель — строки `leads`, счётчик `eb_leads_total`. Но заявки стенда и виджета не различаются: у заявки нет канала и страницы. Знаменатель — веб-аналитика сайта МТС, не наша система. Своё отслеживание посетителей не делаем (роадмап, раздел 4) | Канал и страница сессии — T1, T8; `leads.session_id` — T2; воронка «сессия → заявка» — T6 |
| Доля целевых заявок | Заявки, признанные пресейлом целевыми / все размеченные заявки | Статусов нет. До T5 пресейл размечает вручную по `leads.code` во внешней таблице. Читает заявки ролью `energytool_manager` (`backend/scripts/sql/access.sql`) | Статусы `new / in_progress / done / rejected` и кнопка «Не целевой» — T5 (`000005_lead_status`); оценка `hot / warm / cold` для сравнения с разметкой — T3 |
| Полнота паспорта | Доля заполненных полей чек-листа продукта в заявке | Нет: в `leads` только контакты, комментарий, резюме и диалог | `sessions.passport`, `leads.passport` — T2 (`000003_passport`); полнота в `score` — T3 |
| Время уточняющего звонка | Медиана длительности первого звонка пресейла по заявке, чат против формы | В нашей системе нет. Источник — телефония или CRM МТС, иначе ручной учёт пресейла на выборке заявок | Сократить его должны блоки «Что спросить на звонке» (`missing`, T3) и карточка заявки (T5). Метрика внутренняя: клиенту срок звонка не называется |
| CSAT 👍/👎 | Доля 👍 среди оценённых ответов и доля оценённых ответов | Есть: таблица `feedback` (`rating` −1 / 1, комментарий), кнопки в `/playground` и `/embed`; представление без контактов — `analytics.feedback` | Привязка к каналу и странице — T1; доля 👎 на дашборде — T6, T34 |
| p95 задержки | 95-й перцентиль полного ответа `/api/chat` | Есть: гистограмма `eb_http_request_duration_seconds` в Prometheus — `histogram_quantile(0.95, sum by (le) (rate(eb_http_request_duration_seconds_bucket{route="/api/chat"}[5m])))`. По этапам — `answers.timings` (мс, `server_total`). Корзины грубые (…, 10, 20, 40, 60 с), поэтому p95 приблизительный | Время до первого токена — T13, T32, T34; дашборды Grafana — бэклог T34 |
| Стоимость диалога | Сумма стоимости токенов всех вызовов модели в диалоге: ответы, резюме заявки, извлечение паспорта (T2) | Только суммарный расход шлюза по ключам служб: `/metrics` LiteLLM с меткой `api_key_alias`. Без цен `GW_CHAT_PRICE_IN/OUT`, `GW_EMBED_PRICE_IN` расход нулевой. Делить не на что: число диалогов неизвестно до T1 | `answers.usage` — T34 (`000011_usage`) + сессии T1 → стоимость диалога; её использует T41 |

**Служебные метрики, которые есть уже сейчас** (Prometheus, `backend/internal/metrics/metrics.go`):
исходы ответов `eb_chat_answers_total{outcome}` (`answered`, `fallback`, `core_error`, `broken`, `empty`),
отказы по пределам `eb_rate_limited_total`, заявки без резюме моделью `eb_leads_total{summary_source="digest"}`,
открытые потоки `eb_chat_streams_in_flight`. В Postgres у каждого ответа есть `fallback` и `guard`
(`unknown_numbers`, `repaired`, `stripped`, `dropped`, `too_long`). Тревоги — 7 правил в `monitoring/rules.yml`.

**Сбор метрик**

- `answers` хранится 30 дней, `leads` и `feedback` — 90 дней, ряды Prometheus — 15 дней ([`privacy.md`](privacy.md)).
  Поэтому раз в неделю аналитик выгружает агрегаты без ПДн через роль `energytool_analyst` (схема `analytics`).
  Иначе к концу A/B ранние недели будут удалены.
- Тестовые заявки исключаются: `smoke.sh` создаёт заявку с именем «Смоук» на каждой проверке выкладки.
- Ответы режима автопроверки (`answers.mode`) в метрики пилота не входят.

## 3. Условия остановки

Пороги стартовые: команда их предлагает, а **на shadow они уточняются** по измеренному уровню. Решение об
остановке по ПДн и технике принимает дежурный сразу. По качеству и конверсии решает продукт.

| Условие | Как замеряется | Стартовый порог **[предложение]** | Действие |
|---|---|---|---|
| Любой инцидент с ПДн: утечка, контакты в журнале, чужие данные в ответе, доступ посторонних к `leads` | Сообщение ИБ, дежурного или менеджера | Любой случай | Немедленно снять тег виджета. Runbook T33 «утечка ключа» и «запрос на удаление ПДн», `api forget` ([`privacy.md`](privacy.md)) |
| Ответы без опоры выше порога | Сейчас — доля ответов `chat`, где `answers.fallback = true` или в `answers.guard` есть `stripped` / `dropped`. Позже — доля ответов без опоры (T34) и уверенность (T12) | Больше удвоенного уровня shadow за сутки | Пауза пилота, разбор ответов, исправление и регрессионный кейс |
| Деградация техники | Правило `ChatAnswersDegraded` (больше 20% ответов за 10 минут — не ответ модели, `monitoring/rules.yml`), `ApiDown`, `LlmGatewayDown` | Правило горит дольше 30 минут | Пауза пилота до восстановления; дальше — понятная деградация из T30, когда она будет сделана |
| Рост жалоб | Доля 👎 за неделю; жалобы клиентов, пересказанные менеджерами | Доля 👎 выше уровня shadow в 1,5 раза; любая жалоба на обещание цены, срока или звонка | Разбор за 1 рабочий день; при повторе — остановка |
| Бот пообещал цену, скидку, срок проекта или условия договора | Разметка пресейла; red-team набор T35 | Любой подтверждённый случай | Остановка до исправления и регрессионного кейса |
| Падение конверсии против формы | A/B: целевые заявки на визит в B против A | В A/B — B значимо ниже A (α = 0,05) на промежуточном срезе в середине теста; срез назначается до старта. В пилоте до A/B — сигнал к разбору, не остановка: сравнение с историей страниц ненадёжно | Остановка A/B, разбор воронки (T6) |
| Стоимость | Стоимость диалога (T34); расход ключей шлюза | Выше бюджета, который утвердил продукт. Жёсткий потолок — `GW_KEY_*_BUDGET` | Пауза, разбор: длина контекста, повторы, число вызовов |

## 4. Человек в контуре

| Когда | Что происходит | Есть сейчас | Появится |
|---|---|---|---|
| Клиент просит человека | Заявка менеджеру | Кнопка «Передать менеджеру» и форма (`web/src/components/chat/lead-dialog.tsx`). `CHAT_MODE` в `energybot/prompts.py` просит контакты только после согласия клиента | Заявка прямо в чате с согласием на том же шаге — T2; четыре типа заявки — T17; кнопка всегда в меню виджета — T31 |
| Низкая уверенность | Уточняющий вопрос, затем предложение специалиста | Числовой уверенности нет. Промпт: если база молчит — «в материалах не описано», ближайший факт и предложение специалиста. Guard вырезает числа не из материалов | Метрика уверенности и маршрут `clarify` под флагом `EB_CONFIDENCE_GATE`, только в режиме `chat` — T12. На пилоте предлагаем: при второй подряд низкой уверенности предлагать менеджера **[предложение]** |
| Цена, КП, договор, сроки | Бот не считает и не обещает, а предлагает специалиста | Основание — раздел «Когда требуется специалист» в `knowledge-base/00-reference/02-product-scope-and-limits.md`. Правила промпта: не считать итоговую стоимость, на расчёт или КП предложить менеджера (`CHAT_MODE`). Guard режет числа не из материалов. Детерминированного маршрута нет | Проверка в red-team наборе — T35 (`eval/redteam.jsonl`); отдельная категория в разметке shadow |
| После передачи | Менеджер получает заявку с резюме | `POST /api/lead` → `leads`: контакты, резюме (`summary_source`: `llm` или `digest`), диалог целиком. Заявка сохраняется до резюме, поэтому сбой модели её не теряет. Читается SQL-ролью `energytool_manager`, уведомлений нет | `/manager`, уведомление в Telegram с маскированным телефоном, webhook — T5. Клиенту — номер заявки и «менеджер учтёт удобное время», без срока — T4, T31 |
| Обратная связь от человека | Ошибки бота возвращаются в систему | 👎 с комментарием в `feedback` | Статусы заявок как разметка — T5; «вопросы без ответа» для контент-команды — T6 |

Внутренний ориентир времени реакции пресейла на заявку задаёт продукт. Клиенту этот срок не называется.

## 6. Обновление базы знаний

Markdown через PR → автоматическая регрессия и сверка чисел → выкладка с переиндексацией → версия и откат.

| Шаг | Что происходит | Где | Автоматически? |
|---|---|---|---|
| 1. Правка | Контент-команда меняет Markdown в `knowledge-base/` в ветке от `dev` и открывает PR в `dev` | [`AGENTS.md`](../AGENTS.md) | — |
| 2. Регрессия выборки и сверка чисел | Тест `DatasetTest.test_dataset_is_valid_and_split` прогоняет все кейсы `eval/dataset/cases.jsonl` через `eval/validate_dataset.py` против новой базы. Он проверяет, что раздел из `sources` существует, каждое число эталона есть в цитируемых разделах, а `must` / `must_not` сходятся. Правка убрала или изменила число, на которое опирается эталон, — CI красный. Рядом: `test_guards_present_for_products` (блоки «можно / нельзя утверждать») и `scripts/check_submission.py` | `ci.yml` → `tests/test_offline.py` | да, на каждый PR |
| 3. Сборка и сквозная проверка | Образы всех служб и `smoke.sh` | `backend.yml` | да |
| 4. Регрессия поиска и ответов | `eval/retrieval_eval.py --split dev` до и после правки, без ключей. С ключом — `eval/run_eval.py --with-demo --baseline`. Метрики «до / после» прикладываются в PR | [`AGENTS.md`](../AGENTS.md), раздел «Проверки перед pull request» | нет: в CI не запускается. Предложение — отдельный job `retrieval_eval` на PR, которые трогают `knowledge-base/**`, с условием «не хуже `main`». Workflows правит владелец T36 |
| 5. Эталон устарел | Правка `eval/dataset/parts/*.jsonl` → `validate_dataset.py` → `build_dataset.py`; `cases.jsonl` руками не правится | [`eval/dataset/SPEC.md`](../eval/dataset/SPEC.md) | — |
| 6. Проверка ответа | `energybot/guard.py` берёт допустимые числа из актуальных материалов: новое число в базе бот может назвать, удалённое guard вырежет. Ослаблять проверку без замера нельзя | `energybot/guard.py` | да |
| 7. Выкладка | Слияние `dev` → `main` с approving review. Railway пересобирает `core`: Watch Paths включают `/knowledge-base/**`, включён Wait for CI | [`deploy.md`](deploy.md) | да |
| 8. Переиндексация | На старте ядро считает ключ кеша `<тексты>-<модель>`: хеш id и текста фрагментов плюс отпечаток модели по контрольной фразе. Новый ключ — эмбеддинги пересчитываются и сохраняются атомарно в `EB_INDEX_CACHE_DIR` (`/data/index` на томе Railway). Хранятся текущая и две предыдущие версии (`KEEP = 3`) | `scripts/index_cache.py`, `scripts/core_api.py` | да |
| 9. Версия | `kb_fingerprint` в `GET /api/health` — sha1 от id фрагментов; id включает документ, путь и текст раздела (`energybot/kb.py`), поэтому меняется при любой правке. Первые 8 знаков видны на `/kb`. После выкладки проверить, что отпечаток ожидаемый и `smoke.sh` зелёный | `scripts/core_api.py`, `web/src/app/kb/kb-browser.tsx` | проверка вручную |
| 10. Откат | Revert PR базы и та же цепочка. Ключ кеша совпадает с прошлым, поэтому векторы берутся из кеша без пересчёта, если том смонтирован; без тома — пересчёт на старте, это минуты. Runbook «переиндексация и откат» — см. T33 | `scripts/index_cache.py` | через PR |

**Известная особенность.** id фрагмента меняется при любой правке текста раздела. Ссылки `/kb?chunk=<id>` из
старых ответов и заявок (`answers.sources` в T1) после обновления базы перестанут открывать раздел.
Предложение для T1: сохранять `kb_fingerprint` рядом с `answers.sources`, а на `/kb` показывать «раздел
изменён».

Пробелы базы находят так: сейчас — SQL по `analytics.answers` (запасные ответы, срабатывания guard) и 👎 в
`analytics.feedback`; после T6 — экран «Вопросы без ответа» с группировкой и копированием для контент-команды.

        data-title="Консультант EnergyTool" data-color="#FF0032" data-position="right"
