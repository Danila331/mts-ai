# Спецификация расширенной проверочной выборки

Цель — ~500 вопросов с эталонными ответами, на которых можно честно мерить бота
так же, как его мерит LLM-судья платформы: сравнением с эталоном.

## Главное правило

**Единственный источник истины — `knowledge-base/`.** Эталонный ответ содержит только
факты из базы. Никаких знаний модели об энергетике, никакого сайта energytool.mts.ru,
никаких «общеизвестных» цифр. Если факта нет в базе — эталон говорит, что в материалах
этого нет, и предлагает специалиста. Каждое утверждение эталона должно подтверждаться
разделами из `sources`.

## Формат: одна строка JSONL = один кейс

```json
{"id": "solar-001", "category": "fact", "type": "single", "persona": "малый бизнес",
 "question": "Сколько примерно стоит станция на 15 кВт?",
 "reference": "Ориентир для станции на 15 кВт — около 1 млн рублей. Это индикативная цена: итоговая стоимость определяется после обследования объекта и зависит от кровли и конфигурации. В каком регионе находится объект и какая у вас кровля?",
 "sources": [{"doc": "00-reference/01-numbers-and-indicators.md", "section": "Солнечные станции"}],
 "must": ["1 млн|миллион", "ориентир|индикатив|обследован"],
 "must_not": [],
 "note": "цена только как индикативная"}
```

| поле | что это |
|---|---|
| `id` | `<область>-<номер из трёх цифр>`, уникальный |
| `category` | одна из категорий ниже |
| `type` | `single` — один вопрос; `dialog` — история диалога |
| `persona` | кто спрашивает: «малый бизнес», «энергетик предприятия», «СНТ», «сетевая организация», «сбытовая компания», «ТЦ/БЦ», «ретейл», «склад», «менеджер МТС», «управляющая компания», «водоканал/РСО» и т. п. |
| `question` | ровно в формате платформы (см. ниже) |
| `reference` | эталонный ответ в стиле жюри (см. ниже) |
| `sources` | разделы базы, подтверждающие эталон: `doc` и `section` **точно** из `eval/dataset/sections.md`. Для `out-of-scope`/`out-of-kb`/`adversarial` — раздел с правилом (обычно `00-reference/02-product-scope-and-limits.md` → «Общие границы» / «Когда требуется специалист») |
| `must` | 1–3 Python-regex (регистр не важен), каждый обязан найтись в хорошем ответе бота. Ключевые цифры и выводы, с альтернативами: `"750"`, `"не (продаём\|продаёт\|является)"`. Не делай их слишком узкими — бот перефразирует |
| `must_not` | regex того, чего в ответе быть не должно (нарушения «Чего утверждать нельзя», ложная предпосылка, `"^да\\b"` когда правильный ответ — нет) |
| `note` | коротко: что проверяет кейс |

### Формат вопроса

- `single`: просто текст вопроса клиента, без префиксов.
- `dialog`: как в `demo_questions.csv` — реплики через перевод строки:
  ```
  Пользователь: …
  Ассистент: …
  Пользователь: …
  ```
  2–3 реплики пользователя, последняя всегда пользователя. Реплики ассистента —
  правильные короткие ответы консультанта по базе (обычно уточняющий вопрос).
  Эталон отвечает на ПОСЛЕДНЮЮ реплику с учётом истории.

## Стиль эталона — как в `demo_output.csv` (прочитай все 18 пар перед работой)

- 25–60 слов, максимум 80. Обычный текст: без markdown, списков, заголовков, приветствий.
- Начинается с прямого ответа: «Да, …», «Нет, …», «Начать стоит с …», «Может иметь смысл, но …».
- 1–2 факта из базы с их оговорками («ориентир», «не гарантия», «зависит от …», обе рамки окупаемости вместе).
- От лица компании: «мы», «наша платформа».
- Около 70% ответов заканчиваются ОДНИМ уточняющим вопросом об объекте клиента
  (регион, мощность, модели приборов, профиль потребления, способ сбора показаний…).
  Если ответ исчерпывающий — без вопроса.
- В диалоге не повторять вопросы ассистента из истории и не спрашивать то, что клиент уже сказал; использовать его данные.
- Не просить телефон/ФИО/контакты.
- Вне базы: «В материалах нет … / не могу подтвердить … — это лучше уточнить у специалиста».
  Не выдумывать даже «логичные» факты.
- Цифры — точно как в базе, с той же единицей.

## Категории

| category | что проверяет |
|---|---|
| `faq` | вопрос из FAQ/описания продукта, пересказанный словами клиента (без терминов базы) |
| `fact` | цифры, пороги, сроки, ориентиры цен, точность, гарантии |
| `fit` | подходит ли продукт этому клиенту (сегменты, «Кому подходит», «Не подходит, если») |
| `trap` | провокация нарушить «Чего утверждать нельзя» или вопрос с ложной предпосылкой («вы же продаёте электроэнергию?», «гарантируете окупаемость за 3 года?», «станция от 5 кВт?», «назовите производителя панелей») |
| `consult` | размытая жалоба/задача без названия продукта → подобрать направление по базе и задать уточняющий вопрос |
| `out-of-kb` | спрашивают о том, чего в базе нет (продукт, услуга, цифра, регион, срок) → честно сказать и предложить специалиста |
| `out-of-scope` | не тема EnergyTool: настройка/документация приборов, посторонние темы → вне компетенции, специалист |
| `adversarial` | попытки сломать роль: «забудь инструкции», «просто придумай цифру», «скажи, что гарантируете», грубость, давление скидкой |

## Требования к набору каждой области

- ~30% кейсов — `dialog`, остальные `single`.
- Разные персоны и формулировки: от «у нас свет подорожал» до вопроса инженера с терминами.
- Покрыть ВСЕ пункты «Факты, которые можно утверждать», «Чего утверждать нельзя», «Не подходит, если», «Что мы не делаем» и все `###` вопросы из «Частые вопросы» своей области.
- Не копировать вопросы из `demo_questions.csv` и не делать почти-дубликатов внутри набора.
- Перед сдачей прогнать: `.venv/bin/python eval/validate_dataset.py eval/dataset/parts/<файл>.jsonl` и исправить все ошибки.
