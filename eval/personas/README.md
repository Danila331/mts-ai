# Стресс-тест по персонам (T14)

`eval/personas.py` гоняет сценарные многоходовые диалоги пяти аудиторий кейса с тем же ядром, что отвечает
в веб-чате (`energybot.Consultant`, режим `chat`, стиль `jury` по умолчанию — как `scripts/core_api.py`).
Режим автопроверки и `solution.py` не затрагиваются.

## Сценарии

`scenarios.jsonl` — по строке на сценарий:

| Поле | Смысл |
|---|---|
| `id`, `title` | имя сценария |
| `persona` | `msb`, `engineer`, `snt` (СНТ/УК/ТСЖ), `grid` (сетевая компания), `mts_manager` |
| `start`, `followups` | стартовая реплика клиента и следующие реплики — по порядку |
| `context_turn` | номер реплики клиента (с 1), после которой известны объект и задача |
| `lead_expected` | ждём ли предложения заявки в этом диалоге (у менеджера МТС — нет) |

Клиент не отвечает на вопросы бота — его реплики записаны заранее (без второй модели: дешевле и
воспроизводимо). Реплики написаны так, чтобы правдоподобно продолжать разговор при любом разумном ответе бота.
Темы — из `knowledge-base/`, вопросы `demo_questions.csv` не копируются (это проверяет тест), персональные
данные — только тестовые.

Сейчас: 5 персон × 3 сценария, 57 реплик клиента.

## Запуск

```bash
.venv/bin/python eval/personas.py          # проверка сценариев и оценка цены — модель не вызывается
.venv/bin/python eval/personas.py --mock   # прогон на заглушке API (tests/mock_api.py) — бесплатно

# Настоящий прогон — платный, только с разрешения владельца ядра. Ключи скрипт сам из .env не читает.
set -a; source .env; set +a
.venv/bin/python eval/personas.py --real --publish
.venv/bin/python eval/personas.py --real --persona snt --limit 1   # частичный прогон
```

Цена настоящего прогона (печатается скриптом): по одной генерации на реплику — 57 вызовов чата, плюс перезапрос,
если проверка ядра нашла в ответе число не из материалов (до 114); до 57 эмбеддингов запроса и 57 вызовов
реранкера; эмбеддинги базы — один раз, если нет кэша `index/`. `EB_EVIDENCE`, `EB_CHECK`, `EB_TWO_STAGE`,
`EB_REFINE` добавляют по вызову на реплику.

Отчёт пишется в `eval/reports/personas/<время>.json` (каталог в `.gitignore`). `--publish` (только с `--real`)
кладёт копию в `web/src/app/lab/personas-latest.json`; её показывает страница `/lab` стенда — закоммитьте файл.
Отчёт заглушки опубликовать нельзя: скрипт откажет, а тест проверяет, что закоммиченный отчёт не `mock`.

Почему `web/src/app/lab/`, а не `web/public/`: отчёт импортируется страницей при сборке — схема проверяется
TypeScript-ом и функцией `isReport`, страница остаётся статической, без запроса за файлом и состояния загрузки,
а в standalone-сборку и на Vercel файл попадает сам. Пока прогона не было, в файле заглушка
`{"status": "not-run"}`, и страница честно пишет, что прогон не снимали.

В отчёте нет текстов базы: только реплики диалога, метрики, имена документов и id разделов (ссылки `/kb?chunk=<id>`).

## Метрики и их слабые места

Все метрики — эвристики без судьи-модели.

- **Без чисел вне базы** — доля ответов, где `energybot.guard.unknown_numbers` не нашла чисел, которых нет ни во
  всей базе знаний, ни в репликах клиента (1 и 2 не проверяются). Строже проверки ядра: числа из прошлых ответов
  бота и из примеров эталонов не засчитываются. Слабость: число, которое в базе есть, но относится к другому
  факту (например, порог одного продукта в ответе про другой), проходит как «из базы»; числа словами не ловятся.
- **Уточняющий вопрос** — в ответе есть «?». Слабость: риторический вопрос тоже засчитается, а вопрос не всегда
  уместен — по правилам ответа он нужен, только когда без него не ответить. Поэтому это наблюдение, а не «чем
  больше, тем лучше»; отдельно считается доля диалогов, где вопрос задан в первом ответе.
- **Предложение заявки** — в ответе есть слова о специалисте, менеджере, заявке, контактах, обратном звонке или
  расчёте по объекту (регулярное выражение `LEAD` в скрипте). Слабость: «уточните у специалиста» в отказе
  (`FALLBACK`) тоже считается предложением; у менеджера МТС слово «менеджер» может прозвучать не как приглашение
  к заявке; предложение другими словами («давайте посчитаем ваш объект») может не найтись.
- **Заявка к месту** — по первому ответу с предложением: в ответе на реплику `context_turn` или позже — «вовремя»,
  раньше — «рано», ни разу — «упущена». Для менеджера МТС заявка не ожидается: её нет — норма, есть — «лишняя».
  Слабость: `context_turn` размечен вручную, а скрипт клиента не реагирует на бота — если бот предложил заявку,
  а клиент дальше спрашивает о другом, это не отказ клиента, а запись сценария.
- **Заполнение паспорта** — `null`: паспорта клиента в ядре ещё нет, метрика появится после T2.
- Дополнительно: доля отказов (`FALLBACK` или ошибка), доля ответов, где сработала проверка ядра (перезапрос,
  вырезанные предложения), и число вызовов модели по видам — на каждую реплику и за прогон.
