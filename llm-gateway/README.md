# llm-gateway — шлюз к моделям (LiteLLM Proxy)

Ядро и api ходят к модели не напрямую, а через этот шлюз, и просят модель по псевдониму:

| Псевдоним | Кто зовёт | Что за ним (переменные шлюза) |
|---|---|---|
| `energy-chat` | ядро (ответ), api (резюме заявки) | `GW_CHAT_MODEL` у `GW_BASE_URL` |
| `energy-chat-fallback` | шлюз сам, когда `energy-chat` лежит | `GW_FALLBACK_CHAT_MODEL` у `GW_FALLBACK_BASE_URL` |
| `energy-embed` | ядро (поиск) | `GW_EMBED_MODEL` у `GW_BASE_URL` |
| `energy-rerank` | ядро (поиск) | `GW_RERANK_MODEL` у `GW_BASE_URL` |

Ключ провайдера знает только шлюз. Ядро и api ходят со своими ключами (`GW_KEY_CORE`, `GW_KEY_API`): у каждого
свой список моделей и пределы. Их создаёт `keys.py` при старте шлюза в его базе (`DATABASE_URL`, отдельный
Postgres). Без базы своих ключей нет — службы ходят с `LITELLM_MASTER_KEY`.

**Сменить модель или провайдера** — поменять `GW_*` у службы шлюза и перезапустить её (секунды).
Ядро и api не трогаются. **Включить запас** — задать три переменные `GW_FALLBACK_*`; без них запаса нет.

Сабмит на платформу шлюз не затрагивает: `solution.py` ходит к модели напрямую по переменным платформы.

## Поведение (проверено на 1.108.9 сценариями против фейкового провайдера)

- Параметры, которых LiteLLM не знает (`chat_template_kwargs`, `reasoning`/`provider`, `enable_thinking`,
  `top_k`), доходят до провайдера без изменений (`drop_params: false`).
- 429/5xx/таймаут основного — запрос уходит в запас; после двух сбоев за минуту основной выводится из
  ротации на 30 с, и запросы идут сразу в запас. Без запаса единственный провайдер из ротации не выводится.
- 400 от провайдера уходит клиенту как есть: без запаса и без вывода из ротации
  (`fallback_on_unsupported_params: false`, `BadRequestErrorAllowedFails`). По этому 400 ядро переключает
  формат параметра размышлений.
- Повторов в шлюзе нет (`num_retries: 0`): их делают ядро и api, иначе они перемножаются.
- Эмбеддинги — `/v1/embeddings`, реранкер — `/v1/rerank` (провайдер `hosted_vllm/`).
- Шлюз без модели (`GW_*` не заданы) поднимается и отвечает 400 — ядро отвечает заглушкой. Ядро при этом
  запоминает, что параметр размышлений «не поддерживается»: после настройки модели перезапустите ядро.
- Без `LITELLM_MASTER_KEY` шлюз не стартует. Чужой ключ — 401 (без базы LiteLLM отвечает 400 «No connected db»).
- Ключ api не получает эмбеддинги (403); лишний запрос сверх `rpm_limit` — 429. Повторный старт шлюза обновляет
  ключи, а не создаёт новые. Расход считается по ценам `GW_*_PRICE_*`.
- В журнал расходов не пишутся тексты запросов и ответов (проверено: номер из вопроса в базу шлюза не попал).
- `/metrics` — метрики LiteLLM без ключа (шлюз только в приватной сети): запросы, токены, задержки, расход с
  меткой `api_key_alias` — видно, какая служба сколько тратит.
- Готовность (healthcheck) — `/health/liveliness` и файл `/tmp/gw-ready`, который entrypoint создаёт после
  синхронизации ключей.

## Файлы

- `config.yaml` — модели, запас, повторы. Значения `os.environ/X` подставляет LiteLLM.
- `render.py` — при старте выкидывает деплойменты с незаданными переменными: пустой `api_base` у
  `openai/` означал бы запросы на api.openai.com.
- `entrypoint.sh` — `render.py`, затем `litellm` и `keys.py`. `GW_HOST=0.0.0.0` (на `::` Uvicorn слушает только IPv6, и healthcheck Railway не проходит).
- `keys.py` — ключи служб: модели, `rpm`/`tpm`, одновременные запросы, бюджет.

## Обновление LiteLLM

Версия закреплена в `Dockerfile` (`1.108.9-lts`). Перед сменой — прогнать сценарии: проброс
`chat_template_kwargs`, 400 без запаса, 503 с запасом, эмбеддинги, `/rerank`. LiteLLM выпускается часто, и
поведение запаса и cooldown между версиями меняется.

## Первый старт на хостинге

На пустой базе LiteLLM накатывает 220+ миграций своей схемы: на Railway это ~5 минут. Тайм-аут healthcheck должен
быть больше (600 с), иначе контейнер убьют посреди миграции, она останется failed (Prisma P3009), и шлюз дальше не
стартует — помогает только пустая база. `keys.py` ждёт готовность до `GW_KEYS_WAIT_SEC` (600 с), чтобы ключи
служб создались на том же старте.
