# mts-ai

Репозиторий решения кейса **«МТС EnergyTool: ИИ-консультант для сайта»** в рамках МТС True Tech Hack&Change 2026.

Цель проекта — создать ИИ-консультанта, который понимает задачу клиента, задаёт уточняющие вопросы, подбирает решение, просто объясняет его и передаёт менеджеру заявку с резюме диалога.

## Состав репозитория

- `МТС_кейс.pdf` — исходное описание кейса.
- `knowledge-base/` — распакованная база знаний в формате Markdown.
- `sample_submission/` — распакованный учебный пример решения и его инструкция.
- `demo_questions.csv` — демонстрационные вопросы.
- `demo_output.csv` — пример результатов.
- `requirements.txt` — разрешённый набор зависимостей от организаторов (сабмит может использовать только его).
- `docs/tech-regulations.pdf` — технический регламент организаторов (оригинал): формат сабмита, лимиты, переменные окружения, методика LLM-судьи; `docs/tech-regulations.md` — его текстовая копия для поиска и ссылок.

Архивы распакованы в отдельные каталоги, чтобы файлы примера не перезаписали корневые `README.md` и `requirements.txt`.

> Репозиторий должен оставаться приватным: по правилам кейса базу знаний нельзя публиковать. Для жюри открывается доступ аккаунту `hack-and-change-2026`.

## Стенд одной командой

Развёрнутый стенд: **https://energytool-ai.vercel.app** (фронт — Vercel, бэкенд — Railway, см. [`docs/deploy.md`](docs/deploy.md)).

### Назначение и архитектура

Веб-чат консультанта и виджет для сайта: клиент задаёт вопрос, бот уточняет задачу, отвечает только по базе
знаний с номерами источников и передаёт менеджеру заявку с резюме диалога. Ответы строит то же ядро
`energybot/`, что и решение для автопроверки.

```
браузер ──▶ web (Next, :3000) ──/api/*──▶ api (Go, :8787) ──▶ core (Python, energybot/) ──▶ llm-gateway (LiteLLM) ──▶ провайдер модели
             стенд, виджет, прокси            │ заявки, журнал, пределы
                                             ├──▶ db (Postgres 17)
                                             ├──▶ redis (пределы частоты)
                                             └──▶ prometheus (метрики, тревоги)
```

Браузер ходит только в `web`: адрес и токен API знает сервер Next. Ключ провайдера модели знает только шлюз.
Подробнее о службах — [`docs/deploy.md`](docs/deploy.md), [`backend/README.md`](backend/README.md),
[`web/README.md`](web/README.md); диаграммы C4 и решения (ADR) — задача T33 в [`docs/ROADMAP.md`](docs/ROADMAP.md).

### Запуск

Нужен Docker с Compose v2. Из корня репозитория:

```bash
cp .env.example .env        # вписать LLM_BASE_URL и LLM_API_KEY; .env в git не попадает
docker compose up --build   # → http://localhost:3000
```

Первый старт — несколько минут: ядро считает эмбеддинги базы (дальше берёт их из тома `core-index`). Готовность
всех служб — `docker compose ps` (статус `healthy`). Без ключа стенд поднимается и отвечает заглушкой.
Остановить — `docker compose down`, вместе с данными — `docker compose down -v`.

### Внешний API модели

Стенд ходит к любому OpenAI-совместимому API (на платформе организаторов — их vLLM, локально — например,
OpenRouter). Ключ кладётся в `.env` и уходит только в службу `llm-gateway`; ядро и API получают от шлюза
свои служебные ключи.

| Что | Модель по умолчанию | Переменная |
|---|---|---|
| Адрес API провайдера | — | `LLM_BASE_URL` |
| Ключ провайдера | — | `LLM_API_KEY` |
| Генерация ответов и резюме заявок | `qwen/qwen3.8-27b` | `LLM_MODEL` |
| Эмбеддинги базы | `baai/bge-m3` | `EMB_MODEL` |
| Реранкер | `qwen/qwen3-reranker-8b` | `RERANKER_MODEL` |
| Запасной провайдер (необязательно, нужны все три) | — | `GW_FALLBACK_BASE_URL`, `GW_FALLBACK_API_KEY`, `GW_FALLBACK_CHAT_MODEL` |

Служебные секреты стенда в compose имеют значения для разработки; на хостинге задаются свои:

| Переменная | Назначение |
|---|---|
| `EB_API_TOKEN` | общий секрет прокси Next (`web`) и Go-API; локально можно не задавать |
| `EB_CORE_TOKEN` | общий секрет Go-API и ядра |
| `LITELLM_MASTER_KEY`, `GW_KEY_CORE`, `GW_KEY_API` | ключи шлюза к моделям: мастер-ключ и ключи служб |

Настройки ответа (`EB_TOP_K`, `EB_CONTEXT_CHARS` и др.) — в разделе «Переменные окружения» ниже и в `.env.example`.

### Проверка основного сценария

1. Открыть http://localhost:3000 — откроется `/playground`.
2. Спросить: «Нужен учёт электроэнергии на складе, с чего начать?» — бот задаёт уточняющий вопрос.
3. Ответить на уточнение — ответ опирается на базу, после предложений стоят номера источников. Клик по номеру
   показывает раздел базы, ссылка ведёт на `/kb?chunk=<id>`.
4. Справа — «Отладка ответа»: вкладки «Опора», «Поиск», «Контекст», «Промпт», «Проверка», JSON.
5. «Передать запрос менеджеру» → тестовые данные («Тестов Тест Тестович», `+7 900 000-00-00`) → «Отправить заявку».
   Диалог в сайдбаре помечается значком заявки.
6. Заявка с резюме — в базе (экрана менеджера `/manager` пока нет, задача T5):
   ```bash
   docker compose exec db psql -U energytool -d energytool -c "SELECT code, name, summary FROM leads ORDER BY created_at DESC LIMIT 1"
   ```
7. «Новый диалог» — чистая сессия: бот не помнит прошлый разговор.
8. Виджет: `/widget` — код вставки одной строкой и живое превью.

Связность всех служб одной командой (её же запускает CI):

```bash
sh backend/scripts/smoke.sh http://127.0.0.1:8787 "$EB_API_TOKEN" http://127.0.0.1:3000
```

### Известные ограничения

- Без ключа модели (`LLM_API_KEY`) бот отвечает заглушкой: проверяется связность, а не качество.
- Экрана менеджера, уведомлений и экспорта заявок пока нет — заявки видны в Postgres (T5 в роадмапе).
- Разговоры хранятся на сервере (таблица `sessions`, `GET /api/sessions/:id` с `EB_MANAGER_TOKEN`), но экрана
  для них пока нет — смотреть SQL-запросом или через API (T5). `localStorage` — только кэш интерфейса.
- Глобальные настройки RAG меняет только администратор (`EB_ADMIN_TOKEN`); без входа `/settings` — песочница для
  своих ответов.
- Ответ приходит целиком после проверки, без потоковой выдачи токенов (T13).
- `EB_STAND_URL` (ссылка на копию сайта со страницы `/widget`) подставляется при сборке образа `web`, а не при запуске.
- Факты — только из базы знаний: на вопросы вне базы бот говорит, что данных нет, и предлагает специалиста.

## Решение

```
solution.py                 точка входа автопроверки: questions.csv + knowledge-base.zip → submission.csv
energybot/                  ядро (общее для автопроверки и будущего веб-чата)
  kb.py                     нарезка базы по разделам ##/###, таблицы pandoc → «колонка: значение»
  text.py                   токенизация и лёгкий русский стеммер для BM25, разговорные синонимы
  retrieval.py              BM25 + bge-m3 + реранкер Qwen3 (RRF), подмешивание «можно/нельзя утверждать»
  dialog.py                 разбор «Пользователь:/Ассистент:» в реплики, запросы для поиска
  prompts.py                системный промпт в стиле эталонных ответов
  llm.py                    клиент OpenAI-совместимого API: ретраи, дедлайн, отключение размышлений Qwen3
  guard.py                  проверка ответа: числа только из материалов и диалога, длина
  pipeline.py               вопрос → поиск → промпт → LLM → проверка ответа → постобработка
eval/                       локальный стенд оценки
  dataset/SPEC.md           формат и правила проверочной выборки
  dataset/parts/*.jsonl     кейсы по областям базы (солнце, опт, тарифы, учёт, потери, фото, общее, сквозные)
  dataset/cases.jsonl       собранная выборка с делением dev/holdout
  dataset/sections.md       точные имена разделов базы для ссылок в кейсах
  validate_dataset.py       проверка кейсов: схема, ссылки на базу, цифры эталона есть в цитируемых разделах
  build_dataset.py          сборка частей в cases.jsonl + стратифицированное деление 70/30
  gold_demo.json            какие документы базы нужны для каждого демо-вопроса
  retrieval_eval.py         качество поиска (работает без ключей)
  run_eval.py               прогон как на платформе + стиль + проверки + LLM-судья по методике платформы
  blind_judge.py            слепое судейство (человек или ИИ-агенты): пакеты без указания авторства, ключ отдельно
  codex_judge.py            слепой судья Codex одной командой: ответы → пакеты → Codex → Score
tests/                      офлайн-тесты, включая полный прогон на заглушке API
scripts/build_index.py      предрасчёт эмбеддингов базы в index/ — только для локальной работы, в сабмит не идёт
scripts/build_submission.py сборка плоского dist/submission.zip по регламенту
scripts/simulate_budget.py  бюджет времени: расчётная таблица и прогон на заглушке с задержками
```

### Как отвечает бот

1. Вход разбирается на реплики; для поиска строится запрос с учётом всего диалога.
2. Поиск: BM25 и bge-m3 объединяются через Reciprocal Rank Fusion, затем реранкер упорядочивает 20 кандидатов.
3. Контекст: 10 лучших фрагментов + другие разделы самого релевантного документа в пределах 18 тыс. символов
   (эталон часто опирается на соседние разделы) + «Факты, которые можно утверждать» / «Чего утверждать нельзя»
   для найденных продуктов + общие границы консультации. Обязательные части бюджетом не урезаются.
4. Qwen отвечает по промпту, подогнанному под эталон: прямой ответ, факт из базы, оговорка, один уточняющий вопрос, 30–60 слов, без markdown, без запроса контактов.
5. Проверка ответа: если в нём есть число, которого нет ни в материалах, ни в диалоге (выдумка или запрещённый
   базой расчёт вроде итоговой стоимости), или ответ длиннее 110 слов — один повторный запрос «перепиши без этих
   чисел / короче»; если не помогло — предложения с такими числами вырезаются. На 500 верных эталонах проверка
   против всей базы не срабатывает ни разу, против собранного контекста — в 1,2% (там, где поиск не нашёл раздел).
6. Бюджет времени: по средней длительности ответа решение прогнозирует, успеет ли до дедлайна; если нет — переходит
   в быстрый режим (без реранкера и повторного запроса), а когда на ответ модели времени уже не хватит — отвечает
   выдержкой из самого релевантного раздела. Пустых ответов не бывает.
7. Любая ступень может отказать: без эмбеддингов работает BM25, без реранкера — RRF, при сбое LLM — выдержка из базы.
   `submission.csv` пишется с самого начала, поэтому сабмит валиден даже при падении.

## CI

- `ci.yml` — на каждый PR: `ruff`, тесты, сверка ZIP с регламентом, `actionlint`; TypeScript — когда появится `web/`.
- `backend.yml` — Go-тесты на Postgres и сборка всех образов из `compose.yaml` (включая `web`) со сквозным `smoke.sh`.
- `security.yml` — на каждый PR и раз в неделю: уязвимости зависимостей и образов, SBOM (раздел «Зависимости и их проверка»).
- `release-gate.yml` — на PR `dev → main`: сверка ZIP с регламентом и ревью Codex на соответствие регламенту.
  Прогон бота на выборке и слепой судья в CI не запускаются — оценка качества локально (`eval/lab.py`).
- Vercel — каждое слияние в `main` само выкатывает фронт `web/` на https://energytool-ai.vercel.app.

Слепой судья Codex локально — `python eval/codex_judge.py --set demo --packets 3`.
Секреты, вход Codex по подписке ChatGPT, запуск судьи другим разработчиком и настройка защиты `main` — в [`docs/ci.md`](docs/ci.md).

## Зависимости и их проверка

- **Версии зафиксированы:** Go — `backend/go.mod` и `go.sum` (директива `go` — точный патч, от него зависят
  уязвимости stdlib); npm — `web/package-lock.json`; Python — `solution-requirements.txt` и `requirements-dev.txt`
  с `==`; базовые образы в Dockerfile и `compose.yaml` — тег и `@sha256` digest; GitHub Actions — по SHA коммита
  с версией в комментарии.
- **Проверки (`security.yml`):** `govulncheck` (падает только на достижимых из нашего кода уязвимостях,
  `.github/scripts/govulncheck_gate.py`), `npm audit --audit-level=high`, `pip-audit` по обоим файлам требований,
  `trivy fs` (уязвимости и секреты в репозитории) и `trivy image` по образам `api`, `core`, `web`. Падают HIGH и
  CRITICAL, у которых есть исправление.
- **SBOM:** `trivy fs --format cyclonedx` — артефакт `sbom-cyclonedx` каждого прогона.
- **Обновления:** Dependabot (`.github/dependabot.yml`) раз в неделю присылает PR в `dev` по gomod, npm, pip,
  Docker, compose и Actions; обновления безопасности — сразу.
- **Исключения — только с причиной:** `backend/.govulncheck-ignore` и `.trivyignore`. Сейчас там две уязвимости
  echo v4, исправленные только в echo v5 (обход предела частоты через `X-Forwarded-For`, проброс `X-Real-IP`
  прокси-middleware): у нас адрес для пределов берётся из `X-Client-IP` прокси Next при заданном `EB_API_TOKEN`,
  а прокси-middleware echo не используется. Переход на v5 и проверка доверенного источника адреса — T35.

Локально:

```bash
(cd backend && go run golang.org/x/vuln/cmd/govulncheck@v1.9.0 ./...)
(cd web && npm audit --audit-level=high)
uvx --from pip-audit==2.10.1 pip-audit -r solution-requirements.txt
```

## Быстрый старт

```bash
uv venv -p 3.11 .venv && uv pip install -p .venv/bin/python httpx==0.28.1 numpy==2.2.6
cp .env.example .env   # вписать адрес и ключ API; .env в git не попадает
set -a; source .env; set +a
```

Проверки:

```bash
.venv/bin/python -m unittest discover -s tests -v   # без ключей
.venv/bin/python eval/retrieval_eval.py --verbose   # без ключей — BM25, с ключами — гибрид
.venv/bin/python eval/run_eval.py --with-demo --baseline   # нужен ключ; Score как на платформе, отчёт в eval/reports/
```

Сабмит:

```bash
.venv/bin/python scripts/build_submission.py   # → dist/submission.zip
```

Что важно по регламенту (`docs/tech-regulations.md`):

- платформа переносит только корневые `.py` и `requirements.txt`, поэтому сборка «расплющивает» пакет:
  `energybot/kb.py` → `eb_kb.py` и т. д., импорты переписываются автоматически; индексы и данные в ZIP не кладутся,
  эмбеддинги базы считаются при запуске;
- зависимости сабмита (`solution-requirements.txt`) сверяются с разрешённым набором организаторов;
- лимиты: 5 сабмитов в день, 20 минут на прогон — после `EB_DEADLINE_SEC` (17,5 мин) новые запросы
  к модели не делаются, оставшиеся вопросы получают запасной ответ, файл гарантированно записывается;
- тест `test_flat_zip_runs_like_on_platform` собирает ZIP, распаковывает и прогоняет его на заглушке API;
- бюджет времени проверяется без модели: `scripts/simulate_budget.py` печатает, сколько вопросов успеваем при
  разной скорости модели и `MAX_WORKERS`, и прогоняет решение на заглушке с задержками.

### Переменные окружения

| Переменная | Назначение | По умолчанию |
|---|---|---|
Переменные платформы (на проверке подставляются автоматически, локально — из `.env`):

| Переменная | Назначение | По умолчанию |
|---|---|---|
| `LLM_BASE_URL`, `LLM_API_KEY`, `LLM_MODEL` | OpenAI-совместимый API и модель генерации | модель `qwen/qwen3.8-27b` |
| `EMB_MODEL`, `RERANKER_MODEL` | эмбеддинги и реранкер | `baai/bge-m3`, `qwen/qwen3-reranker-8b` |
| `MAX_WORKERS` | число параллельных обращений, отражает лимиты сервиса | `4` |
| `DATA_DIR` | каталог с `questions.csv` и `knowledge-base.zip` | `data` |

`TOP_K`, `MAX_TOKENS`, `TEMPERATURE`, `CHUNKER`, `RERANKER_TOP_N` платформа тоже передаёт, но они
настроены под бейзлайн — решение их сознательно не читает. Свои настройки — с префиксом `EB_`:

| Переменная | Назначение | По умолчанию |
|---|---|---|
| `EB_TOP_K`, `EB_N_CANDIDATES` | фрагментов в контексте и кандидатов для реранкера | `10`, `20` |
| `EB_EXPAND_DOCS`, `EB_CONTEXT_CHARS` | сколько документов расширять соседними разделами, бюджет контекста | `1`, `18000` |
| `EB_EMBED_BATCH` | размер пачки эмбеддингов; при ответе 400 уменьшается вдвое автоматически | `16` |
| `EB_THINKING_PARAM` | как отключить размышления Qwen3: `chat_template_kwargs` (vLLM, платформа), `reasoning` (OpenRouter), `enable_thinking` (DashScope), `none` | `chat_template_kwargs` |
| `EB_THINKING_BUDGET` | лимит токенов для повтора, если сервер проигнорировал отключение и ответ вышел пустым | `3000` |
| `EB_MAX_TOKENS`, `EB_TEMPERATURE`, `EB_REQUEST_TIMEOUT` | генерация и тайм-аут запроса | `700`, `0`, `60` |
| `EB_USE_EMBEDDINGS`, `EB_USE_RERANKER`, `EB_DISABLE_THINKING` | включение ступеней (`0` — выключить) | `1` |
| `EB_MAX_WORKERS` | переопределить параллельность | `MAX_WORKERS` |
| `EB_DEADLINE_SEC` | общий лимит прогона | `1050` |
| `EMBEDDER_API_KEY`, `RERANKER_API_KEY` | отдельные ключи (как в примере организаторов) | ключ LLM |
| `EB_EMBEDDER_BASE_URL`, `EB_RERANKER_BASE_URL` | только локально: отдельные адреса эмбеддингов и реранкера | адрес LLM |
| `JUDGE_BASE_URL`, `JUDGE_API_KEY`, `JUDGE_MODEL` | отдельная модель для LLM-судьи стенда | как у LLM |
| `DEBUG_JSONL` | путь для источников и времени ответа по каждому вопросу | выключено |

### Проверочная выборка

18 демо-вопросов жюри мало: один вопрос — это ±5,5% к среднему. Поэтому собрана выборка
на ~500 кейсов по всей базе знаний (`eval/dataset/`). Правила:

- источник истины — только `knowledge-base/`; каждый эталон ссылается на разделы базы,
  а валидатор бракует эталон, если в нём есть число, которого нет в этих разделах;
- эталоны в стиле ответов жюри: прямой ответ, факт с оговоркой, один уточняющий вопрос, 25–60 слов;
- у кейса есть `must`/`must_not` — быстрые проверки без LLM (ключевые цифры, ловушки);
- категории: faq, fact, fit, trap, consult, out-of-kb, out-of-scope, adversarial; ~30% — диалоги;
- деление: `dev` (~70%) — для подгонки промпта и поиска, `holdout` (~30%) — контроль переобучения,
  запускать редко.

### LLM-судья стенда

С ответами бейзлайна (`--baseline` или кэш `--baseline-pred`) стенд считает оценку ровно по методике
платформы: каждый вопрос судится дважды с перестановкой «бейзлайн/команда», ориентир — эталон,
шкала 0 / 0,25 / 0,5 / 0,75 / 1, итог `Score = 0,7 · Match Rate + 0,3 · Win Rate`. Без бейзлайна —
абсолютная оценка 0–10 против эталона (для быстрых сравнений, это не метрика платформы).

Ключей организаторы участникам не выдают: модель доступна только внутри проверки. Для локальных прогонов
нужен свой OpenAI-совместимый доступ к модели того же класса (например, Qwen3 ~30B).

### Первый прогон на `qwen3.8-27b` (OpenRouter, 09.11.2026)

360 вопросов (342 рабочей части + 18 демо), бейзлайн — учебный пример организаторов на той же модели,
слепое судейство по методике платформы (судьи — ИИ-агенты, не знающие, где наш ответ):

| набор | Score | Match Rate | Win Rate | победы / ничьи / поражения |
|---|---|---|---|---|
| всё | 0.896 | 0.873 | 0.948 | 331 / 11 / 18 |
| демо жюри | 0.806 | 0.799 | 0.824 | 14 / 1 / 3 |

Слабые места: вопросы вне базы (0.67 — категоричное «нет» или выдумка вместо «в материалах нет»),
выбор продукта (поиск потерь предлагается тем, кому нужна платформа учёта), перенос ценовых ориентиров
между продуктами. Абсолютные цифры не равны баллу платформы: другой судья и другие вопросы.

```bash
python eval/run_eval.py --set dev --with-demo --baseline --no-judge   # ответы бота и бейзлайна
python eval/blind_judge.py export eval/reports/<время> --parts 8      # пакеты для слепых судей
python eval/blind_judge.py score eval/reports/<время>                 # Score по вердиктам
```

## Git Flow

- `main` — продакшен-ветка. Здесь находятся только стабильные и проверенные изменения.
- `dev` — основная рабочая ветка и ветка по умолчанию. Вся разработка ведётся от неё.
- Новую функциональность разрабатываем в отдельных ветках от `dev` и вливаем обратно в `dev`.
- В `main` изменения попадают **только через pull request из `dev`**.
- Для merge pull request `dev` → `main` требуется **минимум один approving review**.
- Прямые push в `main` запрещены. Даже при наличии технической возможности обходить защиту ветки нельзя.
- Перед merge в `main` необходимо убедиться, что изменения проверены и готовы к продакшену.

Правила обязательны для всех участников и AI-агентов; они также зафиксированы в `AGENTS.md`.
